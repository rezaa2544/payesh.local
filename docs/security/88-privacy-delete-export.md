# ۸۸ — حذف/خروج دادهٔ کاربر (حریم خصوصی)

> وضعیت: پیاده‌سازی و آزموده (ردیف ۸۸) روی PostgreSQL واقعی (مسیر ابری محصول) و SQLite (سرور محلی مدرسه).
> ماژول سیاست: `server/privacy.js` · آزمون: `tests/privacy-88.js` (PV-01..PV-19) · CI: `api-contract.yml` گام «Privacy delete/export (row 88)».
> مدت نگهداری **قانونی** داده = تصمیم **OWNER** (بخش ۶).

## ۱. allowlist نقش برای خروجی (بسته)
| نقش | خروجی مدرسه (`POST /api/cloud/tenancy/product/export`) | «دادهٔ من» (`POST …/product/export/me`) | فیلدهای هویتی |
|---|---|---|---|
| manager | کل مدرسه (همهٔ کالکشن‌ها) | فقط ردیف users خودش | دیده می‌شود (تصمیم D1/ردیف ۵۷) |
| teacher، counselor | فقط ردیف‌های درون اسکوپ سرور (ردیف ۳۸: کلاس‌های خودش)؛ users کامل ممنوع (ردیف ۵۷) | ردیف‌های درون اسکوپ | فقط ردیف خودش |
| parent، student | همان؛ ولی فقط فرزند لینک‌شده، دانش‌آموز فقط خودش | خودش (+ فرزند) | فقط ردیف خودش |
| guard و هر نقش ناشناخته | **رد** (`export_role_denied`، 403) | **رد** | — |

- فهرست در `privacy.EXPORT_ROLES` (frozen) است؛ نقشی که در آن نیست هرگز خروجی نمی‌گیرد.
- اسکوپ با همان `scope.rowInScope()` مسیر push اعمال می‌شود (SQL ثابت، بدون SQL پویا).
- رمز/هش/توکن (`password_*`، `phone_hash`، `token*`…) برای **همهٔ** نقش‌ها، از جمله مدیر، حذف می‌شوند (قبلاً خروجی ابری users مدیر `password_hash` را هم می‌داد).
- سرور محلی: `/api/admin/export` پشت سد مدیر است (`/api/admin/*`) و همان قاعدهٔ `exportRow` ردیف ۵۷ را دارد.

## ۲. «کد ملی کس دیگری نه»
برای خروجی غیرمدیر، فیلدهای `policy.USER_IDENTITY_FIELDS` (کد ملی، کد ملی پدر/مادر، شناسنامه، تلفن‌ها، نشانی…) از **هر** ردیف و **هر** کالکشن حذف می‌شوند — نه فقط users — مگر ردیف users خودِ درخواست‌کننده. (آزمون PV-11: یک `national_id` سرگردان داخل ردیف attendance هم حذف می‌شود.)

## ۳. حذف و tombstone
- حذف یک رکورد = tombstone (`deleted_at`) تا دستگاه‌های آفلاین در pull بعدی از حذف باخبر شوند. حذف دستگاه (ابطال + پاک‌سازی از راه دور) از قبل وجود دارد: `DELETE /api/admin/devices/:id` (ردیف ۶۵).
- **نمای حذف‌شده‌ها** (فقط مدیر): `GET /api/cloud/tenancy/product/tombstones` و محلی `GET /api/admin/tombstones` — فقط `collection, id, version, deleted_at`؛ **هرگز بدنهٔ رکورد**.
- **retention**: `PAYESH_TOMBSTONE_RETAIN_DAYS`، پیش‌فرض **۹۰ روز**، کمینه **۳۱**، بیشینه ۳۶۵۰. پاک‌سازی سخت: `POST …/product/tombstones/purge` و محلی `POST /api/admin/tombstones/purge` (بدنهٔ اختیاری `retain_days`؛ کمتر از ۳۱ ⇒ 400 `bad_retain_days`). پس از purge، کد ملی کاربر حذف‌شده دیگر در جدول/فایل پایگاه نیست (PV-05، PV-18).
- چرا کمینه ۳۱: دستگاهی که بیش از `PAYESH_DEVICE_STALE_DAYS` (۳۰) دیده نشده بازنشسته می‌شود و باید دوباره وارد شود (همگام‌سازی کامل)، و change-feed هم ۳۰ روز نگه داشته می‌شود؛ پس tombstone قدیمی‌تر از ۳۱ روز برای هیچ دستگاه زنده‌ای لازم نیست.
- purge فقط مدرسهٔ خودِ توکن را لمس می‌کند (RLS) — PV-18: tombstone قدیمی مدرسهٔ B دست‌نخورده می‌ماند.

## ۴. درخواست بین‌مدرسه‌ای
مدرسه فقط از توکن امضاشده می‌آید. اگر بدنه یا query یکی از `tenant_id` / `tenantId` / `tid` را با مقداری غیر از مدرسهٔ توکن داشته باشد، درخواست با **403 `cross_tenant`** رد می‌شود (قبلاً بی‌صدا نادیده گرفته می‌شد). RLS همچنان پشتیبان است (PV-17).

## ۵. شواهد [S]
`docs/cloud/reports/evidence/88-privacy.txt` — اجرای خام روی PostgreSQL 16.9: `PRIVACY-88-OK checks=16`. دو جهش دستی (حذف اسکوپ از export ⇒ PV-11 قرمز؛ حذف پاک‌سازی هویتی ⇒ PV-02/11/13/14 قرمز) و کنترل منفی PV-19 (همان fixture بدون اسکوپ نشت می‌دهد) نشان می‌دهند سبزبودن تهی نیست.

## ۶. OWNER
- تعیین مدت نگهداری **قانونی** داده (پس از خروج دانش‌آموز/پایان سال) و در صورت نیاز تنظیم `PAYESH_TOMBSTONE_RETAIN_DAYS` (≥ ۳۱).
- زمان‌بندی اجرای purge (دستی از پنل یا cron) در استقرار.
