# ردیف ۱۰۲ — پنل مالک: اجرای محلی با یک فرمان (local-up)

> **فقط برای آزمایش محلی است، نه برای تولید.** این سند استقرار روی سرور را پوشش نمی‌دهد (آن کار ردیف ۱۰۳ است و اجرای واقعی‌اش با ردیف ۱۰۴ و OWNER). همهٔ عددهای این سند از اجرای loopback روی همین دستگاه یا رانر CI به دست آمده‌اند.

## فرمان

```sh
npm ci                                        # یک‌بار در checkout مخزن
node apps/owner-panel/scripts/local-up.js     # ویندوز: apps\owner-panel\scripts\start-owner-local.cmd
```

سپس `http://127.0.0.1:8095` را در مرورگر باز کنید. برای توقف، Ctrl+C را بزنید.

## کاری که فرمان انجام می‌دهد

| گام | رفتار |
|---|---|
| ۱. دیتابیس | به‌طور پیش‌فرض PGlite را در پوشهٔ داده می‌سازد. PGlite یک PostgreSQL جاسازی‌شده است و به نصب جداگانه نیاز ندارد. اگر `DATABASE_URL` داده شود، فقط PostgreSQL همین دستگاه پذیرفته می‌شود: loopback یا سوکت یونیکس، با کاربر superuser محلی. |
| ۲. migration | migrationهای `db/migrations/owner-panel/001..004` را اعمال می‌کند. هر فایل در جدول `public.payesh_owner_local_migrations` با sha256 ثبت می‌شود. ثبت داخل همان تراکنش فایل و درست پیش از `COMMIT` آن انجام می‌شود، پس اعمال و ثبت با هم اتمیک‌اند. اجرای دوبارهٔ فرمان چیزی را تکرار نمی‌کند. اگر فایلی پس از اعمال تغییر کند، فرمان متوقف می‌شود. |
| ۳. رازها | کلید امضای توکن پلتفرم را به‌صورت ۳۲ بایت تصادفی در `secrets.json` می‌سازد. این فایل در پوشهٔ داده و با مجوز 0600 نگه داشته می‌شود و هیچ‌وقت چاپ نمی‌شود. اجراهای بعدی همان کلید را به کار می‌برند. پوشهٔ داده نباید داخل درخت کاری Git باشد. |
| ۴. حساب مالک | فقط یک‌بار ساخته می‌شود. رمز بدون نمایش پرسیده می‌شود؛ در اجرای غیرتعاملی می‌توان آن را با `PAYESH_OPERATOR_PASSWORD` فقط برای همان یک فرمان داد. URI از نوع `otpauth://` هم فقط همان یک‌بار چاپ می‌شود. منطق ساخت حساب همان `create-operator.js` است (D‑45: رمز scrypt، TOTP، سقف ۳ حساب). |
| ۵. سرورها | Gateway واقعی (`server/gateway.js`) را در همان فرایند و فقط با مسیرهای `/api/platform/v1` روی `127.0.0.1:8090` بالا می‌آورد. سرور پنل (`static-server.js`، با CSP و پروکسی same-origin) روی `127.0.0.1:8095` اجرا می‌شود. هیچ اتصالی به دیتابیس مدرسه، replica یا Directory باز نمی‌شود. |

پوشهٔ دادهٔ پیش‌فرض:

| سیستم‌عامل | مسیر |
|---|---|
| ویندوز | `%LOCALAPPDATA%\PayeshOwnerLocal` |
| لینوکس و مک | `~/.local/share/payesh-owner-local` |

با `--data-dir` می‌توان مسیر دیگری داد. پاک‌کردن این پوشه یعنی شروع از صفر.

### اتصال PGlite به Gateway

PGlite آدرس اتصال ندارد. برای همین `server/gateway.js` تابع `usePlatformDb(adapter)` را صادر می‌کند. این تابع فقط از داخل همان فرایند قابل فراخوانی است و از env یا HTTP خوانده نمی‌شود. در دو حالت رد می‌شود: وقتی `PAYESH_PLATFORM_PGURL` تنظیم شده باشد، یا وقتی سرور شروع به گوش‌دادن کرده باشد.

آداپتر هر تراکنش را با `SET LOCAL ROLE payesh_platform_runtime` اجرا می‌کند؛ این همان مرز RLS و grant در تولید است. چون PGlite فقط یک اتصال دارد، تراکنش‌ها با یک mutex پشت سر هم اجرا می‌شوند.

## ردها (کد خروج 2، پیش از ساختن هر چیز)

| ورودی | نتیجه |
|---|---|
| `--host 0.0.0.0` یا هر آدرس غیر loopback | رد |
| `DATABASE_URL` با میزبان غیرمحلی (از جمله `?host=` یا `?hostaddr=` بیرونی، یا طرحی غیر از postgres) | رد |
| `PAYESH_PLATFORM_PGURL` تنظیم‌شده | رد. local-up هرگز به دیتابیس پیکربندی‌شده‌ای که ممکن است تولید باشد وصل نمی‌شود. |
| پوشهٔ داده داخل مخزن Git | رد |
| migration تغییرکرده (sha256 متفاوت) | رد |
| `--smoke` روی پوشه‌ای که حساب مالک دارد | رد. smoke به پوشهٔ تازه نیاز دارد. |

## `--smoke` (CI روی ubuntu-latest و windows-latest)

`node apps/owner-panel/scripts/local-up.js --smoke` این مراحل را اجرا می‌کند:

1. یک پوشهٔ دادهٔ موقت می‌سازد.
2. migrationها را اعمال می‌کند.
3. حساب مالک را می‌سازد. رمز و راز TOTP فقط در حافظه می‌مانند.
4. Gateway و پنل را روی پورت‌های موقت بالا می‌آورد.
5. ورود را از مبدأ پنل آزمایش می‌کند: TOTP غلط باید **401** و رمز همراه TOTP درست باید **200** بدهد.
6. `GET /dashboard` با توکن باید **200** و بدون توکن **401** بدهد.
7. صفحهٔ SPA باید با CSP `frame-ancestors 'none'` سرو شود.
8. خاموشی تمیز: هر دو پورت بسته می‌شوند، دیتابیس بسته می‌شود و پوشهٔ موقت پاک می‌شود.

اگر همه موفق باشد، `LOCAL-UP-SMOKE-OK` چاپ می‌شود. در ویندوز همین smoke از راه `start-owner-local.cmd` هم اجرا می‌شود.

بدون migration 004 (`--migrations-through 003`، فقط برای کنترل منفی)، `POST /auth/login` پاسخ **501 login_not_installed** می‌دهد و smoke قرمز می‌شود.

## آزمون

`apps/owner-panel/tests/local-up.test.js` CLI واقعی را در فرایند فرزند اجرا می‌کند. این آزمون در `npm test`، در `owner-panel.yml` (روی هر دو سیستم‌عامل) و در job `owner-local-smoke` اجرا می‌شود. گیت `owner-gate` به همین job وابسته است.

| شناسه | چه چیزی را بررسی می‌کند |
|---|---|
| LU-01 | bind غیر loopback رد می‌شود. |
| LU-02 | `DATABASE_URL` غیرمحلی رد می‌شود. |
| LU-03 | تنظیم بودن `PAYESH_PLATFORM_PGURL` رد می‌شود. پوشهٔ داده درون Git رد می‌شود. |
| LU-04 | smoke: بنر نمایش داده می‌شود، چهار migration اعمال می‌شود، و هیچ راز یا otpauth در خروجی نیست. `secrets.json` مجوز 0600 دارد. |
| LU-05 | اجرای اول: otpauth دقیقاً یک‌بار چاپ می‌شود، رمز چاپ نمی‌شود، ورود با TOTP همان otpauth موفق است، TOTP غلط 401 می‌دهد، و توقف با سیگنال تمیز است. |
| LU-06 | اجرای دوم idempotent است: `applied=[]`، حساب حفظ می‌شود، otpauth دوباره چاپ نمی‌شود، و توکن اجرای اول هنوز معتبر است (یعنی همان راز استفاده شده). |
| LU-07 | دست‌کاری sha256 در دفتر migration رد می‌شود. |
| LU-08 | بدون migration 004، ورود 501 می‌دهد و smoke قرمز می‌شود. |
| LU-09 | `start-owner-local.cmd` با پایان خط CRLF است، فقط `local-up.js` را اجرا می‌کند، و در بستهٔ وب `payesh-owner-web.zip` هست. |
| LU-10 | همان smoke روی PostgreSQL محلی واقعی با `DATABASE_URL`. فقط وقتی `LOCALUP_PG_URL` تنظیم شده باشد اجرا می‌شود. نتیجهٔ محلی روی PostgreSQL 16.9 در شاهد ثبت شده است. |

کنترل جهش: سه جهش آزموده شد و هر سه را آزمون گرفت:

- حذف بررسی loopback
- نادیده‌گرفتن `DATABASE_URL`
- خاموش‌کردن بررسی checksum

شاهد: `docs/cloud/reports/evidence/owner-local-up-102.txt`.
