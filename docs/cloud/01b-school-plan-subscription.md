## ۱. اصول مدل (غیرقابل مذاکره)

1. **هر موجودیتِ مدرسه‌ای `tenant_id` دارد**؛ کلید اصلی مرکب یا ایندکس اجباری روی `tenant_id` (D‑07).
2. **حالت اشتراک از نشست حل می‌شود، نه از بدنهٔ درخواست.** سرور در هر درخواست، اشتراک همان `tenant_id` را می‌خواند.
3. **اعمال سقف داخل تراکنش** و پیش از ثبت؛ دو درخواست هم‌زمان نباید سقف را بشکنند (D‑19).
4. **هیچ حذف خودکاری** از داده به‌بهانهٔ انقضا (D‑22).
5. **تمدید idempotent** است: همان درخواست دوباره = همان نتیجه، بدون تمدید دوباره.
6. **مالی در v1 فعال نیست** (D‑20) ولی ساختار داده از روز اول هست تا مهاجرت لازم نشود.

## ۲. موجودیت‌ها و طرح جدول‌ها

طرح زیر **مرجع طراحی** است؛ SQLite (اجرای فعلی) و Postgres (مقصد) هر دو را پوشش می‌دهد. `tenant_id` در همه‌جا `TEXT` یکتا (ULID/UUID) است — نه عدد مدرسه.

### ۲.۱ `tenant` (مدرسه)

| ستون | نوع | قید |
|---|---|---|
| `id` | TEXT | **PK** |
| `code` | TEXT | **UNIQUE** — کد کوتاه مدرسه (لاتین کوچک/رقم، ۳–۳۲) |
| `name` | TEXT | NOT NULL |
| `level` | TEXT | CHECK (`primary`,`middle`,`high`,`mixed`) |
| `city` / `province` | TEXT | — |
| `contact_phone` | TEXT | — |
| `status` | TEXT | CHECK (`provisioning`,`live`,`suspended`,`archived`) |
| `storage_prefix` | TEXT | **UNIQUE** — پیشوند اختصاصی ذخیره‌سازی، شامل `tenant_id` |
| `crypto_key_id` | TEXT | کلید فعال مستأجر (نسخه‌دار) |
| `created_at` / `updated_at` | TEXT | ISO |

ایندکس: `UNIQUE(code)`, `UNIQUE(storage_prefix)`, `INDEX(status)`.
قاعده: `storage_prefix` **باید** با `id` شروع شود (`t/<tenant_id>/…`)، وگرنه ساخت مدرسه رد می‌شود.

### ۲.۲ `plan`

| ستون | نوع | قید |
|---|---|---|
| `code` | TEXT | **PK** (مثل `basic`,`standard`,`pro`) |
| `name` | TEXT | NOT NULL |
| `max_users` / `max_students` | INTEGER | NULL = بی‌سقف در آن بُعد (فقط اگر صریحاً مصوب شود) |
| `storage_mb` | INTEGER | سقف فضا |
| `features` | TEXT(JSON) | فهرست قابلیت‌های فعال |
| `price_amount` | INTEGER | **v1: فقط ثبت، فعال‌سازی نه** |
| `price_cycle` | TEXT | CHECK (`monthly`,`yearly`,`none`) |
| `is_public` | INTEGER | ۰/۱ |
| `created_at` | TEXT | — |

قاعده: پلن **حذف نمی‌شود**؛ `is_public=0` + `archived_at` (تاریخچهٔ اشتراک‌ها باید معنا داشته باشد).

### ۲.۳ `subscription`

| ستون | نوع | قید |
|---|---|---|
| `id` | TEXT | **PK** |
| `tenant_id` | TEXT | **FK → tenant.id**, NOT NULL |
| `plan_code` | TEXT | **FK → plan.code** |
| `status` | TEXT | CHECK (`draft`,`provisioning`,`active`,`grace`,`suspended`,`expired`,`canceled`) |
| `starts_at` / `ends_at` | TEXT | NOT NULL |
| `grace_days` | INTEGER | `NULL` تا تصمیم P‑01b‑۱؛ مقدار مؤثر = `COALESCE(subscription.grace_days, config.grace_days)` |
| `auto_renew` | INTEGER | ۰/۱ |
| `canceled_at` | TEXT | — |
| `renewed_from` | TEXT | ارجاع به اشتراک قبلی |
| `version` | INTEGER | برای OCC روی تمدید |
| `updated_at` | TEXT | — |

قیدهای یکتایی و ایندکس:
- **`UNIQUE(tenant_id) WHERE status IN ('draft','provisioning','active','grace','suspended')`** — هر مدرسه در هر لحظه **یک** اشتراک جاری دارد (partial unique index).
- `INDEX(tenant_id, starts_at DESC)` · `INDEX(status, ends_at)` برای کارهای زمان‌بندی‌شده.

### ۲.۴ `subscription_event` (دفتر رویداد وضعیت — الزام تمدید idempotent)

| ستون | نوع | قید |
|---|---|---|
| `id` | TEXT | **PK** |
| `tenant_id` | TEXT | NOT NULL |
| `subscription_id` | TEXT | NOT NULL |
| `from_status` / `to_status` | TEXT | — |
| `reason` | TEXT | CHECK (`payment`,`expiry`,`owner_action`,`cancel`,`renew`,`system`) |
| `actor_id` | TEXT | عامل انسانی یا `system` |
| `idempotency_key` | TEXT | **UNIQUE(tenant_id, idempotency_key)** |
| `at` | TEXT | — |

این جدول هم **audit** است و هم **قفل idempotency**: تمدید دوباره با همان کلید ⇒ همان ردیف برگردانده می‌شود، بدون تغییر وضعیت.

### ۲.۵ `invoice` (ساختار از روز اول، فعال‌سازی پس از O‑15)

| ستون | نوع | قید |
|---|---|---|
| `id` | TEXT | **PK** |
| `tenant_id` | TEXT | NOT NULL |
| `subscription_id` | TEXT | NULL تا فعال‌شدن |
| `period_start` / `period_end` | TEXT | — |
| `amount` / `currency` | INTEGER / TEXT | `IRR` |
| `status` | TEXT | CHECK (`draft`,`issued`,`paid`,`void`,`refunded`) |
| `payment_ref` | TEXT | NULL |
| `issued_at` / `paid_at` | TEXT | — |

ایندکس: `UNIQUE(tenant_id, period_start, period_end)`, `INDEX(status)`.
**قاعدهٔ v1:** هیچ مسیر کاربری/پنلی این جدول را نمی‌نویسد؛ فقط خواندن برای گزارش‌های آینده.

### ۲.۶ `support_grant` (D‑21 — مجوز اضطراری)

| ستون | نوع | قید |
|---|---|---|
| `id` | TEXT | **PK** |
| `tenant_id` | TEXT | NOT NULL (یک مدرسه) |
| `operator_id` | TEXT | NOT NULL (یک اپراتور) |
| `case_ref` | TEXT | ارجاع به مورد/تیکت |
| `reason` | TEXT | NOT NULL (متن اجباری) |
| `scope` | TEXT | CHECK (`metadata`,`content_read`) — `content_write` **مجاز نیست** |
| `starts_at` / `ends_at` | TEXT | `ends_at` **اجباری و ≤ ۷۲ ساعت** |
| `approved_by` | TEXT | NOT NULL — مالک/اپراتور ارشد، **نه خود درخواست‌کننده** |
| `school_notified_at` | TEXT | NOT NULL قبل از شروع |
| `revoked_at` | TEXT | ابطال دستی |
| `used_reads` | INTEGER | شمارندهٔ خواندن |

قیدها:
- `CHECK(approved_by <> operator_id)` — تأیید خودی ممنوع.
- `CHECK(ends_at > starts_at AND ends_at <= max_ends_at)` — `max_ends_at` را **برنامه** هنگام درج محاسبه و ذخیره می‌کند (`starts_at + 72h`).
  دلیل: `datetime(...,'+72 hours')` مخصوص SQLite است و `ends_at <= starts_at + interval '72 hours'` مخصوص Postgres؛ یک CHECK مشترک بین هر دو، فقط با ستون محاسبه‌شده ممکن است. اعتبار `max_ends_at` هم در همان تراکنش با `max_ends_at - starts_at <= 72h` بررسی می‌شود.
- **یک مجوز فعال در هر لحظه برای هر اپراتور** — با ستون `open_slot` (INTEGER، مقدار ۱ تا زمان اعتبار، `NULL` پس از ابطال/انقضا):
  `UNIQUE(operator_id, open_slot)` + `CHECK(open_slot IS NULL OR open_slot = 1)`.
  دلیل: `now()` در شرط ایندکس جزئی **مجاز نیست** (نه در Postgres چون immutable نیست، نه در SQLite چون deterministic نیست). متغیر `open_slot` را کار زمان‌بند در لحظهٔ انقضا `NULL` می‌کند و همان تراکنش یک `support_grant_expired` ثبت می‌کند.
- هر خواندنِ محتوا در `support_access_log` ثبت می‌شود (بلاک ۱۲‑ب).
- **بدون دانلود انبوه:** هر مسیر «list/export» در محدودهٔ مجوز رد می‌شود.

### ۲.۷ `tenant_usage` (شمارنده‌های سقف)

| ستون | نوع | قید |
|---|---|---|
| `tenant_id` | TEXT | **PK** |
| `users_count` / &nbsp;`students_count` | INTEGER | — |
| `storage_bytes` | INTEGER | — |
| `last_recalc_at` | TEXT | — |

قاعده: این جدول **کش شمارش** است، نه مرجع. تصمیم نهایی سقف با `SELECT COUNT(*) … WHERE tenant_id=?` **داخل همان تراکنش نوشتن** گرفته می‌شود؛ شمارنده فقط برای نمایش/هشدار است.

**مرجع حقیقت وضعیت (رفع تعارض دو ماشین حالت):** دو ستون وضعیت وجود دارد و باید تفکیک شوند:

| ستون | دامنه | مرجع چه چیزی است |
|---|---|---|
| `tenant.status` (`provisioning`,`live`,`suspended`,`archived`) | **چرخهٔ عمر مدرسه** روی پلتفرم | فقط برای تأمین/بایگانی/حذف استفاده می‌شود |
| `subscription.status` | **حق استفادهٔ سرویس** | تنها مرجع gate ورود/نوشتن/سقف |

قاعده: gateها **فقط** `subscription.status` را می‌خوانند. `tenant.status` هرگز gate نمی‌گذارد؛ فقط اگر `tenant.status='archived'` باشد، حتی با اشتراک `active` هم سرویس داده نمی‌شود (استثنای صریح بایگانی).

## ۳. چرخهٔ وضعیت (ماشین حالت)

```
draft ──► provisioning ──► active ──► grace ──► suspended ──► expired
                              ▲          │           │
                              └── renew ─┴───────────┘
active ──(owner cancel)──► canceled ──► (پنجرهٔ خروج داده) ──► archived ──(۱۸۰ روز)──► حذف فقط با سیاست مصوب
```

### ۳.۱ جدول گذارها (منبع واحد حقیقت)

| از | به | محرک | مجاز برای | شرط | اثر داده | اثر صف |
|---|---|---|---|---|---|---|
| `draft` | `provisioning` | ایجاد مدرسه | `platform_owner` | فضای اختصاصی + کلید ساخته شود | — | — |
| `provisioning` | `active` | پایان راه‌اندازی | `platform_owner` | کلید مستأجر فعال + `storage_prefix` یکتا | — | — |
| `active` | `grace` | `ends_at` گذشت | سیستم (زمان‌بند) | مقدار مؤثر `grace_days > 0` (وابسته به P‑01b‑۱) | بدون تغییر | می‌پذیرد (هشدار) |
| `active`/`grace` | `suspended` | پایان دورهٔ ارفاقی یا تصمیم مالک | سیستم / `platform_owner` | — | بدون تغییر | **متوقف، حفظ‌شده** |
| `suspended` | `active` | تمدید | `platform_owner` | پرداخت/تصمیم ثبت شود | بدون مهاجرت | **تخلیهٔ امن** (§۵) |
| `grace`/`suspended` | `expired` | تصمیم مالک یا پایان مهلت | `platform_owner` / سیستم | — | حفظ ≥۱۸۰ روز | متوقف، حفظ‌شده |
| `expired` | `active` | تمدید | `platform_owner` | — | بدون مهاجرت | تخلیهٔ امن |
| `active`/`grace`/`suspended` | `canceled` | لغو | `platform_owner` | دلیل ثبت | پنجرهٔ خروج داده | متوقف |
| `canceled` | `archived` | پایان پنجره | سیستم | — | فقط خواندن برای export | — |

**گذارهای ممنوع (باید رد شوند):** `expired → grace` · `canceled → active` (فقط اشتراک **تازه** با `renewed_from`) · هر گذاری بدون `subscription_event` · هر گذاری با کلید idempotency تکراری.

### ۳.۲ رفتار ورود/نوشتن در هر وضعیت (هم‌راستا با D‑22)

| وضعیت | ورود | خواندن | نوشتن/همگام‌سازی | صف | داده |
|---|---|---|---|---|---|
| `active` | ✅ همهٔ نقش‌ها | ✅ | ✅ | ✅ | کامل |
| `grace` | ✅ | ✅ | ✅ + هشدار به مدیر | ✅ | کامل |
| `suspended` | **فقط `school_admin`** | **فقط صفحهٔ اشتراک/تمدید** | ❌ | متوقف، حفظ | کامل |
| `expired` | ❌ هیچ‌کس (نه حتی مدیر)؛ تمدید فقط از پنل پلتفرم | ❌ | ❌ | متوقف، حفظ | ≥۱۸۰ روز |
| `canceled` | ❌ | ❌ (به‌جز مسیر export مجاز) | ❌ | متوقف | پنجرهٔ خروج، سپس بایگانی |
| `archived` | ❌ | فقط مسیر export/خواندن آرشیو برای `platform_owner` | ❌ | متوقف | آرشیو؛ حذف فقط با سیاست مصوب و پس از ≥۱۸۰ روز از انقضا |

**نکتهٔ اجرایی:** «فقط مدیر در `suspended`» یعنی پاسخ ورود سایر نقش‌ها پیام `subscription_suspended` با کد ۴۰۳ است؛ **نه** ۴۰۱ (تا کلاینت آن را «رمز اشتباه» تفسیر نکند).

**نگاشت نقش‌ها (الزامی — واژگان سند با واژگان محصول یکی نیست):**

| نقش در این سند | نقش فعلی محصول (`users.role`) | رفتار در `suspended` |
|---|---|---|
| `platform_owner` | — (پنل پلتفرم، خارج از `users` مدرسه؛ ۱۲‑ب) | مستقل از وضعیت مدرسه |
| `platform_operator` | — (همان) | مستقل از وضعیت مدرسه |
| `platform_support` | — (همان؛ Default Deny طبق D‑24) | مستقل از وضعیت مدرسه |
| `school_admin` | **`manager`** | ورود مجاز، فقط صفحهٔ اشتراک/تمدید |
| `vice_principal` | **در محصول امروز وجود ندارد** (`server/policy.js`: ROLES = manager/teacher/parent/student/counselor/guard) — نقش تازهٔ مقصد | ۴۰۳ `subscription_suspended` |
| `teacher` | **`teacher`** | ۴۰۳ `subscription_suspended` |
| `counselor` | **`counselor`** | ۴۰۳ `subscription_suspended` |
| `student` | **`student`** | ۴۰۳ `subscription_suspended` |
| `parent` | **`parent`** | ۴۰۳ `subscription_suspended` |
| `guard` | **`guard`** | ۴۰۳ `subscription_suspended` |

**قاعدهٔ نگاشت:** فهرست مرجع، **D‑24** است (۱۰ نقش؛ «دفتر/عامل اجرایی» `office` حذف شده). هر نامی که در این سند ≠ نام محصول است، در همین جدول صریح نگاشت شده است: `school_admin → manager`؛ `vice_principal` **در محصول امروز معادلی ندارد** و در پیاده‌سازی مقصد ساخته می‌شود. اگر نام `school_admin` در پیاده‌سازی به‌کار رود، باید در همان لایه به `manager` نگاشت شود؛ در غیر این صورت gate اشتباه ارزیابی می‌کند.

> **اصلاح C‑07 (بازبینی بستن):** نسخهٔ پیشین این جدول ناقص و در دو مورد ناسازگار با D‑24 بود: `vice` و `staff` ذکر شده بودند (در حالی که نام مصوب `vice_principal` است و `office/staff` طبق D‑24 وجود ندارد) و `counselor` و `guard` از جدول جا افتاده بودند. اکنون هر ۱۰ نقش D‑24 ردیف دارد و رفتار `suspended` برای همه صریح است.

## ۴. اعمال سمت سرور (نقاط واقعی، نه رابط کاربری)

### ۴.۱ میدل‌ور اجباری روی هر درخواست

```
resolve tenant از نشست  →  load subscription  →  state gate  →  quota gate  →  handler
```

| گام | قاعده | خطای فارسی |
|---|---|---|
| resolve | `tenant_id` درخواست ≠ نشست ⇒ رد | «دسترسی به این مدرسه مجاز نیست» |
| state gate (نوشتن) | `suspended`/`expired`/`canceled` ⇒ رد | «اشتراک مدرسه غیرفعال است؛ برای تمدید با مدیر پلتفرم تماس بگیرید» |
| state gate (خواندن) | `suspended` ⇒ فقط اشتراک؛ `expired` ⇒ هیچ | «اشتراک مدرسه منقضی شده است» |
| quota gate | سقف کاربر/دانش‌آموز/فضا/قابلیت **داخل تراکنش** | «سقف کاربران پلن شما پر شده است (۳۰۰ از ۳۰۰)» |

### ۴.۲ نقاط دقیق سقف

| عملیات | سقف | لحظهٔ بررسی | پیام |
|---|---|---|---|
| `POST /api/sync` (users, create) | `max_users` | داخل تراکنش، پیش از insert | سقف کاربران |
| `POST /api/sync` (users, role=student) | `max_students` | همان | سقف دانش‌آموز |
| `POST /api/admin/import` | هر سه سقف **پیش از** ثبت کل فایل | ابتدای import | «این فایل از سقف پلن عبور می‌کند: N دانش‌آموز اضافه» |
| آپلود فایل/عکس/بکاپ | `storage_mb` | پیش از نوشتن شیء | «فضای پلن شما پر شده است» |
| هر عملیات قابلیت‌محور | `features[]` | ابتدای handler | «این قابلیت در پلن شما نیست» |
| صف آفلاین | همان سقف‌ها | سرور، هنگام اعمال op | همان پیام‌ها + ثبت `rejected` در پاسخ sync |

**قاعدهٔ حیاتی:** سقف در **سرور** بررسی می‌شود؛ کلاینت فقط پیش‌نمایش می‌دهد. درخواست دستی/مستقیم API هم باید همان رد را بگیرد.

**هم‌روندی (الزام):** «شمارش + درج» باید اتمیک باشد، وگرنه دو درخواست هم‌زمان هر دو از سقف عبور می‌کنند.
- SQLite: تراکنش `BEGIN IMMEDIATE` (قفل نوشتن) — همان الگویی که `server/db.js` استفاده می‌کند.
- Postgres: `SELECT … FROM tenant WHERE id=$1 FOR UPDATE` در ابتدای تراکنش (قفل ردیف مستأجر) و سپس `COUNT(*)` و `INSERT`.
- ترتیب قفل ثابت: همیشه اول `tenant`، بعد جدول هدف — برای پرهیز از deadlock.
- آزمون منفی الزامی: دو درخواست هم‌زمان برای آخرین جای خالی ⇒ یکی ۲۰۰، یکی ۴۰۹ `quota_users`.

---

## ۵. تمدید idempotent و تخلیهٔ امن صف

### ۵.۱ تمدید
1. ورودی: `tenant_id`, `plan_code`, `period`, `idempotency_key`.
2. بررسی `subscription_event UNIQUE(tenant_id, idempotency_key)`:
   - اگر ردیف هست ⇒ **همان نتیجهٔ قبلی** برگردانده می‌شود (بدون تغییر، بدون فاکتور دوم).
   - اگر نیست ⇒ در یک تراکنش: `subscription` به `active` + `ends_at` جدید + `version+1` + `subscription_event` + (در آینده) `invoice`.
3. OCC: اگر `version` فرستاده‌شده با سرور نخواند ⇒ `409 conflict` («اشتراک هم‌زمان تغییر کرد؛ بازخوانی کنید») — نه تمدید دوباره.
4. **اثر جانبی ممنوع:** تمدید هرگز داده را بازنویسی/مهاجرت نمی‌دهد.

### ۵.۲ تخلیهٔ صف پس از تمدید
| مرحله | قاعده |
|---|---|
| ۱ | صف دستگاه‌ها آزاد می‌شود (`paused → draining`) |
| ۲ | ops به ترتیب **وابستگی** ارسال می‌شوند (۰۲ §۵.۲) |
| ۳ | هر op با `applied_ops` idempotent؛ تکرار = همان نتیجه |
| ۴ | op ردشده به دلیل سقف/نقش ⇒ `rejected` **با دلیل**، حذف نمی‌شود؛ کاربر می‌بیند |
| ۵ | op قدیمی‌تر از ۳۰ روز ⇒ «نیازمند بررسی» (D‑27) |
| ۶ | اختلاف نسخه ⇒ «نیازمند تصمیم» (D‑28)، بقیهٔ صف ادامه می‌دهد |

**تضمین:** توقف اشتراک هیچ op را دور نمی‌ریزد و تمدید هیچ op را دوبار اعمال نمی‌کند (بند ۸ و ۹ قانون اساسی).

## ۶. حفظ داده و حذف (D‑22)

| مرحله | مدت | چه اتفاقی می‌افتد |
|---|---|---|
| `expired`/`canceled` | ۱۸۰ روز (حداقل) | داده کامل، فقط خواندنِ مجازِ مالک پلتفرم برای export/پشتیبانی = **فراداده**؛ محتوا ممنوع (D‑21) |
| پایان ۱۸۰ روز | — | **هیچ حذف خودکاری**؛ ورود به فهرست «آمادهٔ بررسی حذف» |
| حذف | — | فقط با: سیاست مصوب مکتوب + اطلاع مدرسه + بررسی الزامات قانونی + ثبت رویداد |

قاعدهٔ نمایش: در پنل مالک، هر مدرسه در وضعیت `expired` باید برچسب «قابل حذف از YYYY‑MM‑DD» بگیرد، ولی دکمهٔ حذف تا تحقق سه شرط غیرفعال است.
