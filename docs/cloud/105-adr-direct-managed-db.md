## ۱. زمینه

مالک هزینهٔ سرور را نمی‌تواند تحمل کند. هدف از ابتدا این بوده است: برنامهٔ کامل روی هر دستگاه نصب شود و بدون اینترنت هم باز شود. برای احراز هویت و تبادل داده فقط یک «حافظهٔ مشترک» در اینترنت باشد. معماری فعلی (بند ۲۵) بین دستگاه و دیتابیس یک Gateway خودمیزبان می‌گذارد. این Gateway یک سرور برای اجرا و نگه‌داری می‌خواهد.

## ۲. تصمیم پیشنهادی

دستگاه‌ها مستقیم با یک **دیتابیس PostgreSQL مدیریت‌شده** حرف می‌زنند. این کار از طریق API و Auth خود ارائه‌دهنده انجام می‌شود، با **RLS** و توابع SQL. هیچ پردازهٔ Gateway خودمیزبانی در مسیر داده نیست.

بند ۲۵ به این شکل بازنویسی می‌شود:

> موتور محلی روی دستگاه کش/نسخهٔ کاری است. هیچ کلاینتی **اعتبارنامهٔ مدیر دیتابیس** یا کلید سرویس (service key) ندارد. فقط کلید عمومی کلاینت + توکن کاربر. هر خواندن/نوشتن از سیاست‌های RLS و توابع SQL می‌گذرد که اسکوپ نقش، `tenant_id`، سهمیه و idempotency را **داخل دیتابیس** اعمال می‌کنند.

## ۳. ستون‌های طرح

### ۳.۱ هویت و سطح دسترسی (هر کاربر شناسه و قابلیت‌های خودش)
- هر کاربر شناسهٔ یکتا (کد کاربر در مدرسه) و ورود با رمز دارد. توکن کوتاه‌عمر را سرویس Auth ارائه‌دهنده صادر می‌کند.
- قابلیت‌ها (capabilities) در جدولی داخل دیتابیس تعریف می‌شوند. مثلاً «ثبت حضور برای کلاس X» یا «دیدن نمرات فرزند Y». ادعای نقش/قابلیت **فقط** از جدول سمت دیتابیس خوانده می‌شود، نه از چیزی که کلاینت می‌فرستد.
- ابطال: ستون `disabled`/`revoked_at` روی کاربر و دستگاه در سیاست RLS چک می‌شود. TTL توکن کوتاه است تا ابطال سریع اثر کند.
- نوشتن قابلیت‌ها فقط با توابع `SECURITY DEFINER` و فقط برای مدیر مدرسه ممکن است.

### ۳.۲ رمزنگاری سرتاسری سمت کلاینت
- ارائه‌دهنده فقط **متن رمزشده** و فراداده‌های لازم برای مسیریابی را می‌بیند: `tenant_id`، شناسهٔ اسکوپ، نسخه، `updated_at`، tombstone.
- فیلدهای حساس (نام، کدملی، نمره، یادداشت) با AEAD سمت دستگاه رمز می‌شوند. AAD شامل `tenant|table|row_id|version` است تا جابه‌جایی ردیف‌ها شناسایی شود.
- سلسله‌مراتب کلید:
  1. کلید مدرسه (SMK) تصادفی است و روی دستگاه مدیر ساخته می‌شود.
  2. هر اسکوپ (مثلاً کلاس) کلید خودش را دارد.
  3. کلید هر اسکوپ برای هر کاربر مجاز با کلید کاربر **wrap** می‌شود. کلید کاربر از رمز (Argon2id/scrypt) و راز بسته به دستگاه (Keystore/DPAPI، ردیف ۷۲) به دست می‌آید.
  4. جدول `key_grants(user_id, scope, wrapped_key)` با RLS فقط ردیف‌های خود کاربر را نشان می‌دهد.
- هم‌خوانی با D‑21: پنل مالک به‌طور پیش‌فرض محتوای مدرسه را نمی‌تواند بخواند، چون کلید ندارد. دسترسی پشتیبانی فقط با اعطای کلید توسط مدیر مدرسه (`support_grant`) ممکن است.

### ۳.۳ منطق Gateway به SQL منتقل می‌شود
- `sync_pull(cursor)` و `sync_push(batch)` به‌صورت RPC با RLS هستند.
- change-feed، idempotency، سهمیهٔ پلن و حل تعارض (LWW + قواعد دامنه) با توابع و تریگر انجام می‌شود. منطق موجود در `server/sync.js`، `tenancy.js` و `outbox.js` مرجع پورت است.
- توابع باید با `SECURITY INVOKER` و RLS اجرا شوند تا نشت اسکوپ ممکن نباشد.

### ۳.۴ کنار گذاشتن Gateway
- کد Gateway موجود در مخزن می‌ماند (برای پشتیبانی از مسیر دوم و کار تاریخی). در مسیر پیش‌فرض اجرا نمی‌شود.
- ارائه‌دهنده باید قابل‌تعویض بماند. توابع و RLS فقط از قابلیت‌های استاندارد PostgreSQL استفاده کنند. بخش وابسته به ارائه‌دهنده (Auth/API) پشت یک لایهٔ نازک سمت کلاینت جدا شود.

## ۴. هزینه‌ها (چیزهایی که از دست می‌دهیم)

| مورد | اثر |
|---|---|
| جست‌وجو/گزارش‌گیری روی فیلد رمزشده در دیتابیس | ممکن نیست. گزارش‌ها سمت دستگاه ساخته می‌شوند. |
| فراموشی رمز | کلید کاربر از رمز می‌آید. بازیابی فقط با مدیر مدرسه یا «کلید بازیابی» آفلاین. اگر هیچ‌کدام نباشد، داده بازیابی‌شدنی نیست. **تصمیم مالک.** |
| لغو دسترسی یک کاربر | برای اینکه کلید قدیمی بی‌اثر شود باید کلید اسکوپ چرخانده شود و داده دوباره رمز شود (re-key). |
| محافظت در برابر DoS/سوءاستفاده | بدون Gateway فقط سهمیه‌های ارائه‌دهنده و تریگرها هستند. با اتمام سهمیهٔ رایگان کل سامانه از کار می‌افتد. |
| ردیف ۸۷ (رمزنگاری سمت سرور) | برای مسیر دوم می‌ماند. در مسیر پیش‌فرض جایگزین آن رمزنگاری سمت دستگاه است. |

## ۵. گزینه‌های ارائه‌دهنده (فقط بررسی، انتخاب با مالک)

منبع این بخش صفحهٔ رسمی Neon و مقالهٔ ثانویهٔ jetadmin برای Supabase است. همه **[E]** هستند و پیش از انتخاب باید با صفحهٔ رسمی تطبیق داده شوند.

| | Supabase (پلن رایگان) | Neon (پلن رایگان) |
|---|---|---|
| حجم دیتابیس | ۵۰۰ MB هر پروژه [E] | ۱ GB هر پروژه [E] |
| توقف | بعد از ۷ روز بی‌فعالیتی pause می‌شود و فعال‌سازی دستی می‌خواهد [E] | compute بعد از ۵ دقیقه بی‌فعالیتی می‌خوابد (بیدار می‌شود)؛ با اتمام سهمیه متوقف می‌شود [E] |
| Auth | تا ۵۰٬۰۰۰ MAU [E] | Better Auth مدیریت‌شده تا ۶۰٬۰۰۰ MAU [E] |
| API مستقیم (PostgREST) | داخل محصول [E] | **[?]** در صفحهٔ بررسی‌شده نیامده |
| پشتیبان | بدون بکاپ خودکار و بدون PITR [E] | ۶ ساعت تاریخچهٔ بازیابی [E] |
| سقف انتقال | ۵ GB egress [E] | ۵ GB انتقال/ماه [E] |

نکته‌ها:
1. دسترسی از ایران، فیلترینگ و تحریم برای هیچ‌کدام بررسی نشده است **[?]**. باید روی شبکهٔ واقعی مالک اندازه‌گیری شود **[M]**.
2. Pause یک‌هفته‌ای Supabase برای مدرسه‌ای که تعطیلات دارد یک خطر عملیاتی است.
3. هیچ‌کدام بدون **بکاپ خارج از ارائه‌دهنده** قابل‌اعتماد نیست (ردیف ۱۱۱).
4. هر پلن پولی فقط با تأیید کتبی مالک (D‑40).

## ۶. کارهای اجرایی (ردیف‌های Notion)
۱۰۶ هویت و RLS · ۱۰۷ رمزنگاری سرتاسری · ۱۰۸ پورت منطق sync به SQL · ۱۰۹ آزمون نفوذ RLS با کلید عمومی · ۱۱۰ transport مستقیم در کلاینت‌ها · ۱۱۱ بکاپ بیرونی و ضدتعطیلی · ۱۱۲ پنل مالک در مسیر مستقیم · ۱۱۳ (مالک) حساب رایگان و اندازه‌گیری دسترسی از ایران · ۱۱۴ صفحهٔ ایستا روی payeshschool.ir. ردیف‌های ۱۰۲–۱۰۴ (local-up، سند استقرار سرور، استقرار واقعی) منسوخ شدند.

## ۷. تصمیم‌هایی که فقط مالک می‌گیرد
1. امضای این ADR و بازنویسی بند ۲۵.
2. انتخاب ارائه‌دهنده (بعد از اندازه‌گیری دسترسی از ایران).
3. سیاست بازیابی کلید: مدیر مدرسه، کلید بازیابی آفلاین، یا پذیرش از دست رفتن داده.
4. پذیرش خطر قطع سراسری هنگام اتمام سهمیهٔ رایگان.

## ۸. وضعیت امنیت
`UNKNOWN`. کلید عمومی کلاینت در هر برنامه‌ای قابل استخراج است. پس **تمام امنیت به درستی RLS و توابع SQL وابسته است**. هیچ ادعای «امن» تا پنتست انسانی (T2) مجاز نیست.
