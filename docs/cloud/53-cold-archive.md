# ردیف ۵۳ — آرشیو دادهٔ سرد و سیاست نگه‌داشت

**وضعیت:** پیاده‌سازی‌شده و آزمون‌شده در همین مخزن؛ شاهد خام در
`docs/cloud/reports/evidence/archive-53.txt` (بازتولید: `bash docs/cloud/reports/evidence/run-53-archive.sh`).
**دامنه:** لایهٔ ذخیره‌سازی محصول (`server/db.js` روی `node:sqlite`) + ذخیره‌ساز شیء سازگار با S3 که کد آن از پیش در مخزن بود
(`client/lib/s3mini.js` و `client/lib/sigv4.js`).
**کارهای انجام‌شده در این ردیف:** سیاست نگه‌داشت مکتوب، جداسازی «پنجرهٔ داغ» از بایگانی سرد، فایل بایگانی خودبسنده و
قابل بازگشت، دسترسی به فایل فقط با نشانی امضاشدهٔ کوتاه‌عمر، و اندازه‌گیری واقعی اندازهٔ جدول‌ها پیش/پس.

> وضعیت امنیتی پروژه با این ردیف **تغییر نمی‌کند** و همچنان **UNKNOWN** است. این سند ادعای ممیزی امنیتی نیست؛
> فقط قرارداد نگه‌داشت داده و سازوکار آرشیو را ثبت می‌کند.

---

## ۱) سیاست نگه‌داشت (retention policy)

قاعده در کد: `server/archive.js` → `POLICY` (تنها منبع حقیقت؛ آزمون `AR-01` مقادیر را قفل می‌کند).

| کمیت | مقدار | معنا |
|---|---|---|
| `hot_months` | **۱۲** | «پنجرهٔ داغ»: فقط ردیف‌های ۱۲ ماه گذشته در جدول داغ می‌مانند |
| `cold_keep_years` | **۷** | عمر نگه‌داشت فایل‌های بایگانی؛ بعد از آن با `purgeExpired` حذف می‌شوند |
| `signed_url_ttl_sec` | **۳۰۰** | عمر پیش‌فرض نشانی امضاشده (۵ دقیقه) |
| `signed_url_max_ttl_sec` | **۹۰۰** | سقف مطلق؛ هر TTL بزرگ‌تر با خطای `ttl_too_long` رد می‌شود |
| `hot_row_threshold` | **۶۰٬۰۰۰** | آستانهٔ پذیرش اندازهٔ جدول داغ در مقیاس شبیه‌سازی‌شده |
| `collections` | attendance, grades, staff_attendance, leaves, announcements, internships | مجموعه‌های مشمول |

منطق: ردیف با `day < cutoff` (یا اگر `day` خالی بود `updated_at < cutoff`) سرد است، که در آن
`cutoff = اولین روز ماه، ۱۲ ماه پیش` (در شبیه‌سازی: `2025-11-01` برای «امروز» = ۲۰۲۶-۱۱-۰۷).

ردیف‌های حذف‌شده (`deleted_at IS NOT NULL`) هیچ‌گاه بایگانی نمی‌شوند؛ آن‌ها موضوع حذف نرم‌اند، نه نگه‌داشت بلندمدت.

## ۲) مسیر داده: داغ → بایگانی → (بازگشت)

```
records (داغ)  ──archiveColdData──▶  s3://<bucket>/<prefix>archive/<collection>/<YYYY-MM>.json
      ▲                                                    │
      └──────────── restoreArchive(store,{key}) ◀──────────┘   (idempotent)
```

**ترتیب امنِ حذف (بدون گم‌شدن داده):** برای هر ماه و هر مجموعه
۱. فایل ساخته می‌شود؛ ۲. `PUT` انجام می‌شود؛ ۳. فایل **بازخوانده** و هش/تعداد ردیف بازبینی می‌شود؛
۴. تنها پس از موفقیت مرحلهٔ ۳، ردیف‌ها در یک تراکنش از `records` حذف و در `archive_manifest` ثبت می‌شوند.
اگر مرحلهٔ ۳ شکست بخورد، هیچ ردیفی حذف نمی‌شود (تراکنش `ROLLBACK`).

**قالب فایل (خودبسنده، بدون وابستگی به SQLite):**

```json
{"v":1,"kind":"payesh-archive","collection":"attendance","month":"2024-02",
 "rows":706,"bytes_raw":...,"sha256":"<hex sha256 روی NDJSON خام>",
 "encoding":"gzip+base64","created_at":"2026-11-07T00:00:00.000Z",
 "data":"<base64(gzip(ndjson))>"}
```

هر خط NDJSON یک ردیف کامل است (`collection,id,version,data,ref1,ref2,day,created_at,updated_at`).
`sha256` روی NDJSON **خام** است، پس سالم‌بودن محتوا مستقل از کانتینر بررسی می‌شود.
بدنهٔ خام gzip به‌عنوان payload در JSON نگه داشته می‌شود چون امضای S3 روی رشتهٔ متنی محاسبه می‌شود و
بدنهٔ دودویی خام در مسیرهای باینری/متنی مستعد خرابی است.

**بازگشت:** `restoreArchive` فایل را می‌خواند، هش و تعداد ردیف را بازبینی می‌کند و ردیف‌ها را با
`INSERT … ON CONFLICT(collection,id) DO UPDATE` برمی‌گرداند؛ دو بار بازیابی داده را تکثیر نمی‌کند
(آزمون `AR-11`) و نسخه/شناسه‌ها دست‌نخورده برمی‌گردند (`AR-10`).

**جدول دفتر بایگانی:** `archive_manifest(key, collection, month, rows, bytes, sha256, created_at, hot_months, restored_at)`.
همین جدول، «کاتالوگ» قابل پرس‌وجو برای بازیابی و برای پایان عمر است.

## ۳) دسترسی به فایل: فقط نشانی امضاشدهٔ کوتاه‌عمر

* مسیر مجاز خواندن یک فایل بایگانی: `signedUrl(cfg,key,{ttlSec})` → `s3mini.presign` → SigV4 با
  `X-Amz-Signature` و `X-Amz-Expires`. پیش‌فرض **۳۰۰ ثانیه**، سقف **۹۰۰ ثانیه** (`ttl_too_long`).
* کلید دائمی (access/secret) هرگز به کلاینت نمی‌رود؛ همان قاعده‌ای که برای بلیت تلفن
  (`D‑23` / `F‑04` — ممنوعیت کلید معلق) اعمال شده، اینجا هم حفظ می‌شود و **تضعیف نشده** است.
* صندوقچه پس از پایان عمر عمومی نیست: `purgeExpired` هم شیء را `DELETE` می‌کند و هم سطر manifest را برمی‌دارد.

## ۵) آزمون‌ها و شاهد

`bash docs/cloud/reports/evidence/run-53-archive.sh` → `docs/cloud/reports/evidence/archive-53.txt` → `ARCHIVE-53-OK`

| شناسه | ادعا |
|---|---|
| AR-01 | سیاست نگه‌داشت مکتوب و قفل‌شده در کد |
| AR-02 | کاشت ۱۲۰٬۰۰۰ ردیف سه‌ساله + اندازه‌گیری پنجرهٔ داغ |
| AR-03 | ذخیره‌ساز شیء، درخواست بدون امضا و امضای جعلی را ۴۰۳ می‌کند |
| AR-04 | `dry-run` هیچ فایلی نمی‌سازد و هیچ ردیفی حذف نمی‌کند |
| AR-05 | آرشیو واقعی با پنجرهٔ ۱۲ ماه |
| AR-06 | همهٔ درخواست‌ها امضای SigV4 معتبر داشتند و هش بدنه تطبیق کرد |
| AR-07 | تراز ردیف‌ها: داغِ قبل = داغِ بعد + بایگانی‌شده (بدون گم‌شدن) |
| AR-08 | جدول داغ فقط پنجرهٔ داغ را دارد (هیچ ردیف سردی جا نمانده) |
| AR-09 | فایل بایگانی خودبسنده و سالم است (gzip + sha256 + تعداد ردیف) |
| AR-10 | بازیابی، شناسه‌ها و نسخه‌ها را برمی‌گرداند |
| AR-11 | بازیابی دوباره داده را تکثیر نمی‌کند (idempotent) |
| AR-12 | فایل دستکاری‌شده بازیابی نمی‌شود (`checksum_mismatch` و `row_count_mismatch`) |
| AR-13 | نشانی امضاشده: معتبر ۲۰۰، منقضی ۴۰۳، TTL بلندتر از سقف رد می‌شود |
| AR-14 | پایان عمر: فایل قدیمی‌تر از ۷ سال حذف می‌شود (هم شیء، هم سطر manifest) |
| AR-15 | اندازهٔ جدول داغ زیر آستانهٔ ثبت‌شده (60,000) |

**آزمون منفی واقعی:** بازبینی امضای SigV4 در `tests/lib/s3-stub.js` مستقل از `client/lib/sigv4.js`
(فقط با `crypto` نود) نوشته شده؛ اگر امضای کلاینت غلط باشد، `PUT/GET` با ۴۰۳ شکست می‌خورد —
پس «موفقیت» آزمون به معنای عبور واقعی از یک بازبین امضاست، نه یک stub بی‌قید.

## ۶) آنچه تغییر نکرده (نگه‌داشت‌های موجود)

* `server/mirror.js` و پشتیبان‌های روزانهٔ `data/backups/daily/payesh-YYYY-MM-DD.json` و
  آینهٔ `data/mirror/*.json` **دست‌نخورده‌اند**؛ آرشیو سرد جایگزین آن‌ها نیست و هیچ فایل پشتیبانی حذف نمی‌شود.
* قاعدهٔ نشانی کوتاه‌عمر (بلیت تلفن `D‑23`/`F‑04`) تضعیف نشد؛ سقف TTL بایگانی هم‌ردهٔ همان قاعده است.
* هیچ ارائه‌دهندهٔ پولی درگیر نشد؛ ذخیره‌ساز شیء همان مسیر ArvanCloud/S3 موجود است.
* `tests/run.js` و دروازهٔ شاهد آن دست‌نخورده‌اند؛ این ردیف شاهد مستقل خودش را دارد.

## ۷) اجرا در محیط واقعی (runbook)

```bash
# ۱) دیدن اینکه چه چیزی سرد است، بدون تغییر
node -e "…archiveColdData(store,{cfg,now,hotMonths:12,dryRun:true})…"
# ۲) آرشیو واقعی (نوشتن، بازبینی، سپس حذف)
node -e "…archiveColdData(store,{cfg,now})…"
# ۳) بازگرداندن یک ماه
node -e "…restoreArchive(store,{cfg,key:'payesh/archive/attendance/2024-02.json'})…"
# ۴) نشانی خواندن کوتاه‌عمر
node -e "…signedUrl(cfg,key,{ttlSec:300})…"
# ۵) پایان عمر
node -e "…purgeExpired(store,{cfg,keepYears:7})…"
```
پیش‌نیاز: پیکربندی صندوقچه در meta (`cloud:config`) یا همان پیکربندی موجود `server/s3mem.js`.
اگر `cfg` نباشد، `archiveColdData` با `storage_not_configured` متوقف می‌شود و هیچ ردیفی حذف نمی‌کند.
