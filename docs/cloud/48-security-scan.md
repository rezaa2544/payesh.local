## ۱) چرا این دروازه «مسدودکننده» است و نه «اختیاری»

معیار پذیرش ردیف ۴۸ صریح است: یافته‌ها باید **CI را قرمز کنند**، نه اینکه در لاگ
ظاهر شوند و کسی نخواند. بنابراین:

- ابزار در همان job بیلد اجرا می‌شود؛ شکست آن = شکست job = عدم امکان انتشار.
- هیچ حالت `continue-on-error` و هیچ `--soft` وجود ندارد.
- «نبود ابزار» هم سبز نیست: اگر semgrep نصب نباشد، اسکنر با کد خروج **۳** می‌میرد
  (نه ۰). در CI نصب با `pip install semgrep` انجام می‌شود.
- «بدون یافته» و «اجرا نشد» از هم تفکیک می‌شوند: خروجی JSON شامل شمارش هر دروازه و
  فهرست یافته‌هاست؛ اگر ابزاری اجرا نشود، کلید آن در JSON وجود ندارد و آزمون قرمز می‌شود.

## ۲) شش دروازهٔ سنجیده‌شده (G1‥G6)

| دروازه | چه چیزی | آستانه (قرمز می‌شود اگر) |
|---|---|---|
| **G1** وابستگی تولیدی | `npm audit --omit=dev` | هر یافتهٔ `high`/`critical` — **بدون هیچ استثنا** |
| **G2** وابستگی dev | `npm audit` (کامل) | یافته‌ای که در `tools/deps-allowlist.json` با دلیل + `expires` نیست، یا `expires` گذشته باشد |
| **G3** SAST الگویی | `tools/semgrep/rules.yml` روی `server/** client/** tools/** scripts/** bench/** tests/**` | هر یافتهٔ severity `ERROR` |
| **G4** SAST taint | `tools/semgrep/taint-rules.yml` روی `server/**` | هر یافتهٔ `ERROR` (تزریق SQL / فرمان از ورودی HTTP) |
| **G5** هشدارها | شمارش per-rule در برابر `tools/semgrep/triage.json` | قاعده‌ای که تریاژ نشده، یا تعداد از سقف ثبت‌شده گذشته باشد |
| **G6** رازِ ثابت | الگوهای کلید/توکن روی خروجی `git ls-files` | هر راز واقعی در فایل ردیابی‌شده |

### چرا G2 استثنا دارد و G1 ندارد

هفت یافتهٔ `high` فعلی همه **dev-only** و از زنجیرهٔ ابزار تست‌اند
(`lodash`/`lodash-es`/`chevrotain*`/`java-parser` — از مسیر `prettier-plugin-java`).
رفع آن‌ها نیازمند ارتقای major است و تا آن زمان در allowlist با **دلیل مکتوب و تاریخ
انقضا** ثبت شده‌اند؛ انقضا خودکار دروازه را قرمز می‌کند پس استثنا نمی‌تواند بی‌صدا
ابد شود. برای وابستگی تولیدی چنین دری وجود ندارد — چون این کد روی دستگاه دانش‌آموز
و مدرسه اجرا می‌شود و «high در runtime» قابل پذیرش نیست.

## ۳) سیاست تریاژ هشدارها (G5) — «رشد خاموش ممنوع»

تری‌اژ به‌صورت **سقفِ هر قاعده** است، نه اثر انگشت هر خط:

```json
{ "rules": { "innerhtml": { "max": 15, "reason": "…", "reviewed_at": "2026-11-08" } } }
```

- افزودن یک مورد جدید از همان قاعده تا زمانی که سقف پر نشده مجاز است (خط‌های کد جابه‌جا
  می‌شوند و اثر انگشت خطی شکننده است)، اما **عبور از سقف = قرمز**.
- قاعدهٔ تازه که در `triage.json` نباشد = قرمز (`untriaged`).
- هر سقف باید `reason` و `reviewed_at` داشته باشد؛ سقف بدون دلیل در آزمون رد می‌شود.
- پس هر افزایش سقف یک تصمیمِ ثبت‌شده در PR است، نه یک اتفاق.

موارد تریاژشدهٔ کنونی: `innerhtml` (۱۵)، `sql-string-concat` (۹)، `weak-crypto` (۴)،
`plaintext-http` (۱). دو مورد اول مستند به این واقعیت‌اند که `server/scope.js`
(`sqlPredicate`) و `client/*` با `esc()`/`$n` و ثابت‌های داخلی مقدار می‌سازند، نه با
درج رشتهٔ خام کاربر.

## ۴) پنج کنترل منفی — دروازه واقعاً قرمز می‌شود؟

سبز بودن یک دروازه وقتی هیچ چیز بدی وجود ندارد اثباتِ ضعیفی است. پس آزمون، پنج نسخهٔ
خراب از همین مخزن (کپی hardlink در `/tmp`) می‌سازد و **باید** آن‌ها را رد کند:

| شناسه | تزریق | انتظار |
|---|---|---|
| SS-07 | `eval()` روی ورودی HTTP در سرور | `gate=RED` با `eval` |
| SS-08 | SQL ساخته‌شده از `req.body` | `gate=RED` با `sql-taint` |
| SS-09 | کلید ثابت با پیشوند `AKIA…` در سورس | `gate=RED` با `aws_access_key` |
| SS-10 | کم‌کردن سقف تریاژ یک قاعده | `gate=RED` با `untriaged warnings` |
| SS-11 | تزریق وابستگی dev عمداً آسیب‌پذیر (lodash 4.17.15) در کپی package-lock + allowlist منقضی | `gate=RED` با `expired allowlist` |
| SS-11b | همان وابستگی بدون مدخل allowlist (قرمز)، سپس با مدخل معتبر (G2 سبز) | `unlisted=RED, listed=G2 green` |

اگر هر یک از این کنترل‌های منفی سبز شود، دروازه **شکست‌خورده** است — حتی اگر مخزن واقعی
پاک باشد.

## ۶) این سند چه چیزی را ادعا **نمی‌کند**

- **pentest مستقل انسانی روی مسیر ابری انجام نشده است.** SAST الگویی و taint فقط
  خطاهای کلاس‌های شناخته‌شده را می‌گیرد؛ منطق دسترسی، IDOR، و جریان‌های چندمرحله‌ای
  احراز هویت را ابزار پیدا نمی‌کند.
- «همهٔ یافته‌های P0/P1 بسته شده‌اند» ادعا نمی‌شود، چون فهرست یافته‌های انسانی وجود
  ندارد. هیچ پذیرش ریسکی برای P0/P1 هم در این ردیف ثبت نشده است.
- CodeQL استفاده نشده است: مخزن خصوصی است و CodeQL برای repo خصوصی نیاز به GitHub
  Advanced Security دارد. معادل انتخاب‌شده semgrep + `npm audit` + اسکن راز است که
  همین دروازه را می‌سازد. این جایگزینی آگاهانه است، نه فراموشی.

## ۷) بخش بازِ ردیف (OWNER) — شرط رسیدن به Done

| مورد | مالک | شرط بستن |
|---|---|---|
| pentest مستقل روی مسیر ابری (school/manager/owner panel + sync) | OWNER (بودجه/انتخاب تأمین‌کننده) | گزارش مکتوب + هر یافتهٔ P0/P1 یا بسته شده یا با «پذیرش ریسک» امضاشده |
| تغییر وضعیت «امنیت» از UNKNOWN | OWNER | فقط با همان گزارش — نه با سبز شدن CI |

تا آن زمان ردیف ۴۸ در وضعیت **Review** می‌ماند: بخش ماشینی Done و مسدودکننده، بخش
انسانی باز.
