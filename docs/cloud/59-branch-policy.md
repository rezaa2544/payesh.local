# ردیف ۵۹ — سیاست اجرا روی شاخهٔ قفل‌شده (D-38): یک PR برای هر ردیف + merge توسط مالک

**وضعیت:** Done (سیاست + ابزار سنجش + آزمون با کنترل منفی).
**ابزار:** `node tools/branch-policy-59.mjs [--pr-audit --rows 60,59]` · **آزمون:** `npm run test:branch59` (BP-01..BP-12)

## سیاست (لازم‌الاجرا از `2026-11-08T02:00:00Z`)

1. **B1 — شاخه:** کار روی شاخهٔ مجری، هرگز روی `main`. این «توقف §۹» نیست؛ کار ادامه دارد.
2. **B2 — وضعیت مرجع:** `origin/main` است؛ قبل از هر کار `git fetch` و شاخه نباید از آن عقب باشد.
3. **B3 — force-push ممنوع:** نوکِ شاخه روی origin باید جدِ `HEAD` باشد؛ تاریخ بازنویسی‌شده ⇒ قرمز.
4. **B4 — سلامت main:** هر کامیت روی `main` یا merge است (و کامیت‌هایش از راه merge آمده‌اند)
   یا کامیت خودکار انتشار (`chore(release)`). کامیت ویژگی مستقیم روی `main` ⇒ قرمز.
5. **B5 — یک PR برای هر ردیف:** هر شمارهٔ ردیف باید دقیقاً یک PR ادغام‌شده داشته باشد؛ اصلاح‌ها
   به **همان PR** push می‌شوند، نه PR دوم.

D-38 یعنی «merge توسط مالک/CI» — نه «توقف کار تا تأیید».

## ۵) نکتهٔ اندازه‌گیری (اصلاح همین دور)

فهرست PR برای ردیف‌های قدیمی عنوان‌هایی مثل «بستهٔ استقرار ابری برای تست ۶۰ روزه» را
با «ردیف ۶۰» قاطی می‌کرد (PR 17 به‌غلط PR ردیف ۶۰ شمرده می‌شد). حالا اگر عنوانِ
صریح «ردیف n» وجود داشته باشد فقط همان‌ها شمرده می‌شوند و عددِ لخت فقط زمانی
به کار می‌رود که هیچ عنوان صریحی نباشد — سنجهٔ BP-11 همین را قفل می‌کند.

همچنین `--pr-audit` حالا `--state all` می‌گیرد: PR باز هم «یک PR برای این ردیف» است،
وگرنه B5 تا لحظهٔ merge همیشه قرمز می‌ماند و شاهد پیش از merge هرگز سبز نمی‌شد (BP-12).

## ۶) استثنای main در CI (پیگیری همین ردیف)

دروازهٔ سیاست شاخه در `build.yml` با `if: github.ref != 'refs/heads/main'` اجرا می‌شود:
B1 («کار روی main ممنوع») ذاتیِ شاخه‌های کاری است و روی main هر کامیت همان merge یا
انتشار خودکار است که B4 از سمت شاخه می‌سنجد. بدون این استثنا، هر merge به main
CI را قرمز می‌کرد (اجرای ۴۲۴۴۹۲۱۶۹۷۲ همین را نشان داد).
