## ۱. زمینه
- مالک هزینهٔ سرور جدا را فعلاً نمی‌پذیرد. هاست ابری فعلی (RadCloud) از قبل پرداخت شده است [A].
- تصمیم نهایی مالک «Backend/API یا مسیر امن معادل» را می‌خواهد. دسترسی مستقیم و ناامن کلاینت به دیتابیس هم ممنوع است.
- بنابراین:
  - مسیر پیش‌فرض یک **Gateway/API بی‌حالت و چندمستأجری** است.
  - داده در یک **PostgreSQL مرکزی با RLS** نگه داشته می‌شود؛ هر مدرسه یک tenant است.
  - اپ بومی Flutter **offline-first** است و SQLite، outbox و sync دارد.
- پنل مالک نقش Control Plane را دارد: ثبت ارائه‌دهنده، سلامت، ظرفیت، هشدار و ممیزی.

## ۲. تصمیم
1. **مسیر داده:** دستگاه → Gateway/API (HTTPS) → PostgreSQL (RLS؛ `app.tenant_id` در هر تراکنش).
   - بند ۲۵ بی‌تغییر است.
   - هیچ کلاینتی اعتبارنامهٔ دیتابیس ندارد.
2. **Provider-agnostic:**
   - فقط از قابلیت‌های استاندارد PostgreSQL استفاده می‌شود.
   - نشانی اتصال فقط از محیط خوانده می‌شود (`DATABASE_URL` و `PGBOUNCER_URL`).
   - بخش وابسته به ارائه‌دهنده (سلامت، ظرفیت، API پنل) پشت یک لایهٔ نازک قرار می‌گیرد (ردیف ۱۲۲، migration 005 پنل مالک).
   - تعویض ارائه‌دهنده = تغییر env + انتقال داده با ابزار ردیف‌های ۵۴ و ۱۱۱.
3. **Fallback مسیر مستقیم:**
   - کد ردیف‌های ۱۰۶ تا ۱۱۱ می‌ماند.
   - `client/transport.js` در نبود `PAYESH_TRANSPORT=direct` (یا با هر مقدار نامعتبر) Gateway را انتخاب می‌کند.
   - فعال‌سازی = امضای ADR‑105 به‌دست مالک.
4. **اعلان:** با Polling هوشمند (D‑46) و بدون FCM اجباری.
5. **مرحله‌ای بودن:** فقط پس از سبز شدن دروازهٔ هر مرحله با شاهد برچسب‌دار به مرحلهٔ بعد می‌رویم. در مرحلهٔ A هیچ سرویس پولی‌ای در کار نیست.

## ۵. نگاشت ردیف‌ها به مراحل
- **A:**
  - ۱۱۵ (پروب)، ۱۱۶ (OWNER: اجرای پروب)، ۱۱۷ (همین سند)، ۱۱۸ (تطبیق Done با مخزن)، ۱۱۹ (آفلاین)، ۱۲۰ (استقرار؛ وابسته به ۱۱۶)، ۱۲۱ (مدرسه ← tenant)، ۱۲۲ و ۱۲۳ (لایهٔ زیرساخت و صفحهٔ «زیرساخت» پنل مالک؛ فاز ۱ ثبت دستی + سلامت محدود)، ۱۲۴ (پژوهش API ارائه‌دهنده‌ها).
  - اگر هاست PostgreSQL نداشته باشد، ردیف ۱۱۳ (OWNER: حساب رایگان) هم به A تعلق دارد.
- **B:** ۷۴ (صفحه‌های بومی روی ترابری Gateway)، ۹۴ (سند نصب و راه‌اندازی)، ۶۱ و ۹۱ (کلید و Secret = OWNER)، ۹۲ (پنتست = OWNER).
- **C و D:** فقط با شاهد [M] از مرحلهٔ قبل و تأیید کتبی هزینه. هنوز ردیفی برای آن‌ها باز نشده است.

## ۶. داده، بازیابی و آفلاین (خلاصه؛ جزئیات در ردیف‌های ۱۱۸ و ۱۱۹)
- **نوشتن روی دستگاه:** تراکنش SQLite محلی + outbox ماندگار (ردیف ۴۰) → push idempotent از Gateway (`op_id`) → ثبت در PostgreSQL با RLS → change-feed → pull با مکان‌نمای ماندگار (ردیف ۳۶).
- **در قطعی شبکه، Gateway یا DB:** صف روی دستگاه می‌ماند. backoff با jitter و احترام به `Retry-After` برای 429 و 503 اعمال می‌شود. پس از برگشت شبکه، اجرای خودکار صف انجام می‌شود. وضعیت همگام‌سازی برای کاربر دیده می‌شود.
- **در از دست رفتن دیتابیس:** بکاپ رمزشده خارج از ارائه‌دهنده + مانور بازیابی (ردیف ۱۱۱). نسخهٔ محلی مدیر (بند ۴.۴) مرجع کمکی است.

## ۷. پیامدها و ریسک باقی‌مانده
- مرحلهٔ A به یک هاست اشتراکی وابسته است. همیشه‌روشن بودن، ماندگاری دیسک و سقف منابع آن تا ردیف ۱۱۶ **[?]** است. اگر هر کدام قرمز شود، مسیر A با PostgreSQL مدیریت‌شدهٔ رایگان ادامه می‌یابد. اگر Gateway هم روی هاست ممکن نباشد، تصمیم با مالک است (ارتقا فقط با تأیید کتبی).
- ردهٔ رایگان ارائه‌دهنده‌ها سقف و توقف دارد (ADR‑105 §۵ [E]). بکاپ بیرونی (ردیف ۱۱۱) اجباری است.
- دسترسی از شبکه‌های ایران به هر ارائه‌دهندهٔ بیرونی **[?]** است. باید با پروب ۱۱۵ (`outbound_tls_pg`) و ردیف ۱۱۳ روی شبکهٔ واقعی سنجیده شود.
- امنیت **`UNKNOWN`** است تا پنتست انسانی انجام شود (D‑41).

## ۸. تصمیم‌هایی که فقط مالک می‌گیرد
1. هر خرید یا ارتقا (VPS، VPC، VGC، دیتابیس پولی) و ورود به مراحل C و D.
2. تغییر DNS دامنهٔ `payeshschool.ir`.
3. امضای ADR‑105 (فعال‌سازی مسیر مستقیم).
4. انتخاب ارائه‌دهندهٔ PostgreSQL رایگان (ردیف ۱۱۳)، اگر هاست PostgreSQL نداشته باشد.
5. Go/No‑Go پایلوت.
