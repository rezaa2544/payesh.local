## 1. هدف و مرز

ساخت یک اپ مدیریتی مستقل از پنل مدرسه، با ورود، سطح نقش، مسیر API، build و انتشار جدا. این اپ فقط فرادادهٔ پلتفرم را مدیریت می‌کند؛ پیش‌فرض دسترسی محتوایی آن **رد** است. تنها استثنای محتوایی، `support_grant` معتبر با تأیید و اطلاع‌رسانی لازم و ثبت هر خواندن در `support_access_log` است. هیچ مسیر کلاینتی مستقیماً به دیتابیس متصل نمی‌شود؛ مسیر داده از Gateway می‌گذرد. مالی/پرداخت و رابط کاربری فاکتور خارج از v1 هستند؛ نگهداری ساختار داده‌ای `invoice` به‌تنهایی مجاز است.

پنل مدرسهٔ ناحیهٔ A خارج از دامنه است؛ `client/pages.js` نباید تغییر کند. سرویس پنل در مسیر/دامنهٔ اپ مدرسه ارائه نمی‌شود. امنیت تا پنتست انسانی مستقل `UNKNOWN` می‌ماند؛ آزمون‌های خودکار جای آن را نمی‌گیرند.

## 2. نگاشت پیشنهادی قابلیت‌ها به API و داده

نام‌های مسیر زیر **پیشنهادی‌اند**؛ قرارداد نهایی باید پیش از پیاده‌سازی API تثبیت شود. همهٔ مسیرها زیر Gateway و یک namespace جدا مانند `/api/platform/v1/` قرار می‌گیرند؛ هیچ route نباید از API مدرسه برای احراز هویت یا اختیار استفاده کند.

|---|---|---|---|
| ۱. داشبورد | `GET /dashboard` | `tenant`, `subscriptions`, `tenant_limits`, `tenant_usage`, رخدادهای فراداده | فقط شمارش/وضعیت/هشدار؛ بدون محتوای مدرسه |
| ۲. مدارس | `GET /tenants`, `GET /tenants/{id}`, `POST /tenants/{id}/suspend`, `POST /tenants/{id}/activate`, درخواست حذف | `tenant`, درخواست‌های حذف، `platform_audit` | operator فقط تعلیق با دلیل؛ owner فعال‌سازی؛ حذف با چهارچشمی و مهلت حداقل ۲۴ ساعت |
| ۳. پلن/اشتراک | `GET/POST /plans`, `GET /subscriptions`, عملیات تمدید/تغییر وضعیت | `plans`, `subscriptions`, `subscription_event`، `invoice` فقط ساختاری | چرخهٔ ۰۱‑ب §۳ و idempotency؛ پرداخت/صدور فاکتور در v1 غیرفعال |

### 2.1 قرارداد داده و مجوز پیشنهادی

- جداول پلتفرمی از جداول محتوای مدرسه جدا می‌مانند. هویت پلتفرم در `platform_users` نگهداری می‌شود و هر ردیف مدرسه‌ای دارای `tenant_id` است. هیچ صفحهٔ وب اجازهٔ اتصال مستقیم به PostgreSQL ندارد.
- دسترسی Gateway به داده‌های tenant-bound، `tenant_id` را از هویت/نشست معتبر می‌گیرد و در لایهٔ داده با RLS محدود می‌کند. سیاست‌های جدول‌های platform-wide باید جدا و صریح باشند؛ نقش platform به معنی دسترسی به ردیف محتوایی نیست.
- جداول پیشنهادی برای PR‑1: `platform_users`, `plans`, `subscriptions`, `subscription_event`, `tenant_limits`, `tenant_usage`, `support_grant`, `support_access_log`, `platform_audit`, و `invoice` غیرفعال. مهاجرت باید نسخه‌دار و برگشت‌پذیر باشد.
- قیدهای `support_grant` از ۱۲‑ب §۳ و ۰۱‑ب §۲.۶: `scope` فقط `metadata` یا `content_read`؛ `content_write` با CHECK رد شود؛ دلیل حداقل ۱۰ نویسه؛ `ends_at` حداکثر ۷۲ ساعت پس از شروع؛ `approved_by` غیرتهی و متفاوت از درخواست‌دهنده؛ `school_notified_at` پیش از شروع؛ grant غیرقابل‌تمدید؛ ابطال فوری؛ هر read محتوایی لاگ مستقل.
- درخواست/تأیید/اطلاع‌رسانی grant مرحله‌های جدا هستند. تفاوت نام فیلد «اطلاع» و «تأیید مدیر مدرسه» در متن‌های ۱۲‑ب/۰۱‑ب و prompt باید پیش از migration روشن شود؛ این سند تفاوت را به تصمیم جدید تبدیل نمی‌کند.
- عملیات پرقدرت دلیل متنی و رویداد ممیزی hash-chained می‌خواهند. پاک‌سازی یا حذف مدرسه خودکار نیست و retention/اطلاع/قانون باید رعایت شود.

### 2.2 مرزبندی نقش‌ها

قانون اساسی D‑24 واژگان `platform_owner`, `platform_operator`, `platform_support` را به‌عنوان نقش‌های پلتفرم و جدا از `users.role` مدرسه ثبت کرده است. این prompt نام‌های کوتاه `owner`, `operator`, `support` را به‌کار می‌برد. پیشنهاد این سند: هیچ نام پلتفرمی وارد `ROLES` مدرسه نشود؛ نگاشت نام API/UI به نقش‌های canonical فقط پس از تأیید مالک ثبت شود. در انتظار آن، هیچ role enum یا مسیر مجوزی تغییر نمی‌کند.

## 3. اپ مستقل، رابط و پوسته

- نامزد مسیر منبع: `apps/owner-panel/`؛ SPA ایستا، فارسی/`fa-IR`، RTL، بدون وابستگی اجرایی به `client/pages.js`، بدون CDN، بدون فونت یا اسکریپت خارجی.
- صفحه‌ها: ورود/TOTP، داشبورد، مدارس، پلن و اشتراک، سقف/مصرف، سلامت فراداده، اپراتورها/grant، گزارش، امنیت/ممیزی. هر صفحه باید حالت loading، empty و error و مجوز سمت سرور داشته باشد.
- عملیات خطرناک: دلیل اجباری، تأیید دوباره، audit؛ حذف مدرسه چهارچشمی + ۲۴ ساعت تأخیر. operator نه در UI و نه در API اجازهٔ تمدید/حذف ندارد.
- هویت بصری باید از «نبض» بیاید، نه رنگ سرمه‌ای پایه. منبع بررسی‌شده `client/pulse.css` است؛ لوگو از `client/icons/logo.png`/`logo-mark.png` و آیکون‌ها SVG خطی محلی هستند. برای اپ مستقل، فونت Vazirmatn باید محلی بسته‌بندی و مجوز OFL در `THIRD_PARTY_LICENSES` ثبت شود؛ در مخزن فعلی فایل Vazirmatn پیدا نشد.
- manifest مستقل: `theme_color=#0d9488` و `background_color=#eef7f5`. تاریخ در UI جلالی و در داده ISO ذخیره شود؛ ارقام فارسی. اپ هیچ آدرس Gateway یا token را در build hard-code نمی‌کند.

### 3.1 اختلاف توکن‌ها — نیازمند تطبیق پیش از PR‑3

خود prompt، `client/pulse.css` را مرجع حقیقت می‌نامد، اما اعداد توکنِ همان prompt با فایل فعلی یکسان نیستند. نمونه‌های مستقیم از فایل فعلی: `--radius:18px` در برابر `16px`؛ `--muted:#91b1a8` در برابر `#7fa39a`؛ `--line:#203b35` در برابر `#16302b`؛ `--primary-2:#2dd4bf` در برابر `#0d9488` در حالت تاریک. فایل فعلی همچنین `--accent` دارد، نه `--acc`، و `--ring`/`--shadow` را تعریف می‌کند. پس PR‑3 نباید ادعا کند «تطابق دقیق با نبض» تا مرجع/مقادیر با مالک تثبیت و در آزمون مقایسه‌ای ثبت شوند. هیچ رنگی در این سند به‌عنوان تصمیم جایگزین انتخاب نشده است.

## 4. تصمیم‌های باز — پیشنهاد، نه تصمیم

### O‑27 پیشنهادی — D‑44 پیشنهادی: فناوری و بسته‌بندی اپ پنل مالک

1. **احراز هویت:** پیشنهاد بررسی: جدول مستقل `platform_users`; رمز با `crypto.scrypt`; نشست کوتاه‌عمر و refresh چرخشی؛ TOTP اجباری برای owner با RFC 6238 و بدون dependency اجرایی خارجی؛ rate limit و audit برای ورود/revoke. این فقط گزینهٔ پیشنهادی است. O‑17 موجود در قانون اساسی نیز دربارهٔ MFA پنل مالک باز است.
2. **پوسته/بسته‌بندی:** گزینهٔ A، بسته‌بندی دسکتاپ و Android جدا با build محلی و استقرار وب مستقل؛ گزینهٔ B، Flutter مستقل در صورت پذیرش ابزار/SDK و هزینهٔ CI؛ گزینهٔ C، PWA تنها (برای نیاز فعلی فایل نصبی کافی نیست). هیچ گزینه‌ای تصویب نشده است.
3. **استثنای WebView:** اگر برای پنل مالک پوستهٔ WebView2/Android WebView انتخاب شود، ADR باید صریحاً بگوید این استثنا فقط برای ابزار مدیریتی مستقل است؛ ردیف ۶۳ و دروازهٔ استقلال بومی کلاینت مدرسه تغییر نمی‌کند.
4. **مسیر/شناسهٔ محصول:** نامزد `apps/owner-panel/`; نامزد endpoint `/api/platform/v1/`; نام‌های نهایی و app identifiers به ADR واگذار می‌شوند.
5. **انتشار و امضا:** نام Secretها فقط در مستند build ذکر شوند، نه مقدارشان؛ نبود Secret باید خروجی واضح unsigned/test-only یا شکست fail-closed بسازد. نصب واقعی و signing فقط پس از پیکربندی Owner ممکن است.

**توالی شناسه:** Decision Log قانون اساسی D‑37 می‌گوید Dها ترتیبی‌اند و آخرین D موجود در آن `D‑42` است؛ `ADR‑43` نام یک سند است، نه ثبت خودکار `D‑43`. بنابراین عنوان `D‑44` در این پیشنهاد هنوز تخصیص قطعی نیست و باید پیش از ثبت، ترتیب D‑43/D‑44 و O‑27 در Decision Log/Notion توسط Owner بررسی شود. این سند قانون اساسی یا Decision Log را تغییر نمی‌دهد.

## 5. ابهام دامنه و شماره‌گذاری

این پیشنهاد قابلیت‌های جدول v1 همین prompt را به‌عنوان دامنهٔ کاری ثبت می‌کند، اما یک ناسازگاری شماره‌گذاری با اسناد موجود دارد: قانون اساسی §۴.۸ می‌گوید بخش‌های ۱–۷ و ۹–۱۰ و بخش ۸ مالی خارج از v1 است، ولی فهرست همان بخش در §۴.۸ و جدول `12b-owner-panel-boundaries.md` §۲.۱ بعضی شماره‌ها را به مالی/گزارش/امنیت متفاوت نسبت می‌دهند و دسترسی اضطراری در §۳.۲ آمده است. نام قابلیت‌ها هم‌پوشانی دارند اما شماره‌ها یکی نیستند. پیش از آنکه شمارهٔ بخش معیار پذیرش CI یا Notion شود، این نگاشت باید با مرجع مالک هماهنگ شود؛ این سند محتوای دامنه را گسترش نمی‌دهد و هیچ شماره‌ای را بی‌صدا اصلاح نمی‌کند.

## 6. ترتیب مرحله‌ای پیشنهادی

- **PR‑0 (این سند):** طراحی و پرسش‌های باز، بدون کد. وضعیت این سند صرفاً Proposal است.
- **PR‑1:** مدل داده، RLS، migration برگشت‌پذیر و آزمون‌های CHECK/نشت؛ شامل نگاشت شماره‌دار E1–E16 از شواهد slice‑20b. این مرحله باید فقط schemaهای جدید/زیرساخت مقصد را لمس کند و هیچ دادهٔ مدرسه را تغییر ندهد.
- **PR‑2:** API پلتفرم پشت Gateway، auth/role مستقل، rate-limit/request-id/OpenAPI و آزمون‌های منفی default-deny. پیش از اجرای حقیقی هر مسیر محتوا، grant و access-log باید در data layer اجباری باشند.
- **PR‑3:** SPA مستقل، توکن‌های نبضِ تطبیق‌یافته، قلم/مجوز محلی، نقش‌های UI + server-side authorization و آزمون jsdom/Playwright. `client/pages.js` خارج از تغییر است.
- **PR‑4:** buildهای Windows/Android/Web جدا و release assetهای ثابت؛ امضا فقط با GitHub Secrets مالک؛ app identity و مسیر نصب جدا از اپ مدرسه.
- **PR‑5:** ردیف‌های جدید دانلود بالای README بدون شکستن ردیف‌های موجود؛ گیت هم‌ترازی README↔workflow↔assets/checksum و بررسی HEAD لینک‌ها. پاسخ شبکه‌ای که واقعاً اجرا نشده `NOT-RUN` می‌ماند.
- **PR‑6:** نقشه/ROADMAP/Ground Truth، ردیف‌های Notion با لینک شاهد، و شاهدهای جدید با `base_sha=`، فرمان، خروجی خام و برچسب `[S]`/`[M]`/`[E]`/`[A]`/`[?]` متناسب با واقعیت.

هر PR باید فقط فایل‌های همان مرحله را تغییر دهد، با آزمون منفیِ مربوط، خودبازبینی و CI سبز. هیچ PR یا مرحله‌ای به‌تنهایی مجوز ثبت تصمیم Owner، ادعای امنیت، یا ادعای نصب واقعی نیست. نصب Windows/Android، بصری‌سنجی روی دستگاه، امضای ADR/Secrets و T2 پنتست انسانی فقط Owner است.
