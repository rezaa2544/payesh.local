## چرا لازم است

در مسیر مستقیم، داده روی یک PostgreSQL مدیریت‌شده می‌نشیند. در پلن رایگان، خودِ ارائه‌دهنده پشتیبان نمی‌گیرد. اگر پروژه متوقف یا قفل شود، تنها نسخهٔ داده در دسترس نیست. پس یک نسخهٔ مستقل، **بیرون از ارائه‌دهنده**، لازم است. باید هم بتوان آن را بازیابی کرد و هم اثبات کرد که بازیابی کار می‌کند.

نتیجه‌ها:

- dump روزانه خودش فعالیت پایگاه‌داده است و احتمالاً جلوی توقف را می‌گیرد. اما منابع می‌گویند ping به‌تنهایی همیشه کافی نبوده است. پس **به آن تکیه نمی‌کنیم.** فرمان `status` ‏(بخش «پایش») هر جا dump متوقف شود هشدار می‌دهد.
- تصمیم دربارهٔ پلن پولی یا رایگان با مالک است (ردیف ۱۰۵/۱۱۳).

## چه چیزی پشتیبان گرفته می‌شود

- `pg_dump -Fc -n payesh_direct`: کل اسکیمای مسیر مستقیم، شامل جدول‌ها، داده، sequenceها، تابع‌ها، policyهای RLS و GRANTها.
- `pg_dump -Fc -t public.payesh_schema_migrations`: دفتر مهاجرت‌ها، تا بعد از بازیابی بشود ادامهٔ مهاجرت‌ها را اجرا کرد.
- **محتوای رکوردها حتی داخل dump هم رمز e2e1 است** (ردیف ۱۰۷). کلید آن فقط روی دستگاه‌هاست. پشتیبان یک لایهٔ رمز دوم روی کل فایل اضافه می‌کند، چون فراداده هم حساس است: شناسه‌ها، کلاس و دانش‌آموز، زمان‌ها، دفتر دستگاه‌ها و audit.

## قالب فایل و کلیدها

- **رمزنگاری:** X25519 (کلید یک‌بارمصرف برای هر فایل)، HKDF-SHA256 و AES‑256‑GCM در تکه‌های ۱ مگابایتی.
  - nonce هر تکه شمارنده است.
  - AAD هر تکه از hash سرآیند، شمارنده و پرچم «تکهٔ آخر» ساخته می‌شود.
  - تکهٔ آخر manifest را نگه می‌دارد: اندازه و sha256 هر بخش، و snapshot شمارش‌ها.
- **dump مستقیم از pg_dump به رمزگذار stream می‌شود.** هیچ dump سادهٔ رمزنشده‌ای روی دیسک ماشینِ پشتیبان نمی‌نشیند.
- **کلید عمومی** (`payesh-backup.pub`) روی ماشین پشتیبان است. فقط با آن می‌شود رمز کرد و نمی‌شود باز کرد.
- **کلید خصوصی** (`payesh-backup.private.key`، با مجوز 0600) **آفلاین و نزد مالک** می‌ماند، مثلاً روی USB در گاوصندوق، با یک نسخهٔ دوم جدا. فقط برای بازیابی لازم است.
  - **اگر کلید خصوصی گم شود، همهٔ پشتیبان‌ها بی‌استفاده می‌شوند.**
  - اگر کلید خصوصی لو برود، باید یک جفت کلید تازه ساخت (`keygen`)، از آن به بعد با کلید تازه dump گرفت و پشتیبان‌های قدیمی را امحا کرد.
- **نام فایل** به وقت UTC است: `payesh-backup-YYYYMMDDTHHMMSSZ.e2b`. کنار هر فایل یک sidecar ‏`.json` هست که اندازه، sha256 و kid را نگه می‌دارد و هیچ رازی ندارد.
- `.gitignore` این‌ها را بیرون نگه می‌دارد: `*.e2b`، `payesh-backup.private.key`، `backups/` و `*.key`. **هیچ رازی وارد مخزن نمی‌شود.**

## اجرا (روی ماشینی که مالک انتخاب می‌کند)

```
# یک بار: کلیدها (کلید خصوصی را بلافاصله آفلاین کنید)
node tools/backup-111.mjs keygen --out-dir ./keys

# هر بار: رشتهٔ اتصال فقط از متغیر محیطی خوانده می‌شود، نه از argv
export PAYESH_BACKUP_SOURCE_URL='…'   # از مدیر رمز عبور؛ هرگز در فایل مخزن
node tools/backup-111.mjs dump --pub ./keys/payesh-backup.pub --out-dir /path/to/backups
node tools/backup-111.mjs verify --file /path/to/backups/payesh-backup-….e2b
node tools/backup-111.mjs prune --dir /path/to/backups --keep 7 --monthly 6
node tools/backup-111.mjs status --dir /path/to/backups --max-age-hours 36   # exit 1 = هشدار
```

### نقش پشتیبان‌گیری

جدول‌های `record` و `sync_*` ‏RLS اجباری (FORCED) دارند. نقشی که این قابلیت را نداشته باشد فقط بخشی از داده را می‌بیند و dump ناقص می‌شود، بی‌آنکه خطایی بدهد. برای همین **ابزار پیش از شروع بررسی می‌کند که نقش، superuser یا BYPASSRLS باشد، و در غیر این صورت متوقف می‌شود** (`backup_role_needs_bypassrls`).

باید روی پروژهٔ واقعی تأیید شود **[M]/OWNER**:

- کدام نقشِ ارائه‌دهنده این ویژگی را دارد؛
- آیا می‌شود یک نقش جداگانهٔ فقط‌خواندنی با BYPASSRLS برای پشتیبان ساخت؛
- رشتهٔ اتصال مستقیم یا session pooler کدام است. transaction pooler برای pg_dump مناسب نیست.

### نسخهٔ pg_dump

pg_dump باید هم‌نسخه یا تازه‌تر از سرور باشد. اگر pg_restore تازه‌تر از سرور مقصد باشد (مثلاً ۱۷ در برابر ۱۶)، ابزار خودش از مسیر «اسکریپت SQL + psql در یک تراکنش» می‌رود و فقط سطر `SET transaction_timeout` را حذف می‌کند. تمرین محلی دقیقاً همین حالت را گذرانده است.

### زمان‌بندی

زمان‌بندی را مالک روی ماشین منتخب تنظیم می‌کند: Task Scheduler ویندوز روی رایانهٔ مدرسه، یا cron. مثال cron:

```
15 2 * * *  cd /opt/payesh && . ./backup.env && node tools/backup-111.mjs dump --pub keys/payesh-backup.pub --out-dir /backups && node tools/backup-111.mjs prune --dir /backups
0 9 * * *   cd /opt/payesh && node tools/backup-111.mjs status --dir /backups || <هشدار به مالک>
```

### بسامد و حجم

پیش‌فرض یک dump در روز است، با نگهداری ۷ نسخهٔ روزانه و آخرین نسخهٔ هر ماه تا ۶ ماه. این یعنی RPO حداکثر ۲۴ ساعت.

داده‌ای که در این فاصله از دست برود هنوز روی دستگاه‌ها هست، در outbox یا موتور محلی، و پس از بازیابی دوباره push می‌شود. uid ثابت باعث می‌شود چیزی دوبار نوشته نشود. تمرین همین را نشان داد: پخش دوبارهٔ یک uid پس از بازیابی `duplicate` برگرداند.

با رشد داده، ترافیک خروجی dump را با سقف پلن مقایسه کنید (جدول خطر بالا).

## محل نگهداری — تصمیم مالک (OWNER)

گزینه‌ها پیشنهادی‌اند و انتخابی انجام نشده است. Cloudflare به‌خاطر D‑09 کنار گذاشته شده.

1. **رایانهٔ مدرسه + یک USB یا دیسک خارجی که هر هفته جدا نگه داشته می‌شود.** ساده است و بیرون از ارائه‌دهنده است. اما خطر آتش‌سوزی یا سرقت در همان ساختمان را دارد.
2. **دو محل:** رایانهٔ مدرسه، به‌اضافهٔ یک فضای ذخیره‌سازی دیگرِ غیر از ارائه‌دهندهٔ پایگاه‌داده که مالک انتخاب کند. چون فایل رمز است، میزبان فایل چیزی نمی‌بیند.
3. **ماشین شخصی مالک.**

هر گزینه‌ای انتخاب شود، **کلید خصوصی نباید کنار فایل‌ها باشد.**

## بازیابی (Runbook)

1. یک PostgreSQL خالی آماده کنید: محلی، یا پروژهٔ تازهٔ همان یا دیگر ارائه‌دهنده.
2. فایل را بررسی کنید: `verify --file F` (checksum)، سپس `verify --file F --key K` (رمزگشایی کامل).
3. بازیابی کنید:

   ```
   export PAYESH_RESTORE_TARGET_URL='…'
   node tools/backup-111.mjs restore --file F --key K [--create-roles]
   ```

   - مقصد باید خالی باشد. اگر اسکیمای `payesh_direct` یا دفتر مهاجرت در آن باشد، ابزار رد می‌کند (`target_not_empty`).
   - روی یک cluster تازه، `--create-roles` دو نقش NOLOGIN و NOBYPASSRLS به نام‌های `payesh_direct_owner` و `payesh_direct_client` می‌سازد. بدون این گزینه، ابزار پیش از هر تغییری متوقف می‌شود (`roles_missing`).
   - بازیابی در **یک تراکنش** و با توقف روی اولین خطا انجام می‌شود.
   - پس از آن، شمارش جدول‌ها، پرچم‌های RLS، تعداد policyها، تابع‌ها، GRANTها و دفتر مهاجرت با snapshot مهرشده داخل پشتیبان مقایسه می‌شود. هر اختلافی خطاست (`restore_mismatch`).
   - فایل‌های موقت رمزگشایی‌شده (مجوز 0600) بازنویسی و حذف می‌شوند.
4. در لایهٔ API ارائه‌دهنده، نقش احراز هویت را عضو `payesh_direct_client` کنید و کلید عمومی و URL تازه را به دستگاه‌ها بدهید (ردیف ۱۱۰).
5. دستگاه‌ها از `since=0` pull می‌کنند. outbox هر دستگاه آنچه را بعد از آخرین پشتیبان نوشته شده بود دوباره می‌فرستد.

## محدودیت‌ها

- **[M]/OWNER:** این موارد روی پروژهٔ واقعی ارائه‌دهنده آزموده نشده‌اند: نقش BYPASSRLS، رشتهٔ اتصال، TLS ‏(`sslmode=require` پیش‌فرضِ میزبان غیرمحلی است) و زمان dump روی دادهٔ واقعی.
- پشتیبان فقط مسیر مستقیم را می‌پوشاند (`payesh_direct` و دفتر مهاجرت). auth خودِ ارائه‌دهنده، یعنی کاربران و رمزهای ورود، در این dump نیست. پس از بازیابی روی پروژهٔ تازه، نگاشت `sub` کاربران باید دوباره برقرار شود (ردیف ۱۰۶، `app_user.sub`). این کار مالک است.
- RTO اندازه‌گیری‌شده روی دادهٔ آزمایشی کمتر از یک ثانیه است و برای دادهٔ واقعی معیار نیست.
