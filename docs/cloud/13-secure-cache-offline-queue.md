## ۱. سه مخزن محلی، سه قاعدهٔ متفاوت

| مخزن | چیست | مرجع؟ | عمر | رمزنگاری |
|---|---|---|---|---|
| **Cache** | کپی خواندنی از اسکوپ کاربر | ❌ هرگز | `min(۷ روز, پایان نشست/ابطال)` | AES‑GCM با کلید غیرقابل‌استخراج |
| **Queue** | عملیات تأییدنشدهٔ کاربر | ❌ تا adjudication | تا تأیید/ابطال، **بدون حذف خودکار** | همان کلید (متن + متادیتا) |
| **Backup** | ۱۴ نسخهٔ روزانهٔ مدیر | ❌ | ۱۴ نسخهٔ چرخشی | همان کلید |

هیچ‌کدام «نسخهٔ دومِ حقیقت» نیستند. حقیقت = ردیف سرور با `tenant_id` (۱۲ §۴).

## ۲. چرخهٔ عمر کش (باگ F‑09/F‑07 در مقصد منتفی)

```
ورود موفق ──► ساخت کلید نشست (WebCrypto non-extractable)
             └─► کش فقط برای `tenant_id` فعال
هر پاسخ pull ──► upsert با `server_seq`
پایان نشست / ابطال / W1 ──► پاک‌سازی کش **قبل از** TTL  (قاعدهٔ ۰۳)
۷ روز گذشت ──► پاک‌سازی خودکار (فقط کش)
تغییر مدرسه ──► تخلیهٔ کامل (کش + صف + کلید)
```
- TTL بر پایهٔ `last_session_end` **و** `cached_at` محاسبه می‌شود؛ هرکدام زودتر.
- نشان `revoked_before(ts)` از سرور: هر ردیف با `server_seq` قدیمی‌تر از آن اعمال نمی‌شود.
- ابطال سمت سرور (W1) بی‌درنگ اعمال می‌شود حتی اگر دستگاه آفلاین باشد؛ در اولین اتصال اجرا می‌شود.

## ۳. صف عملیات — قرارداد مقصد

### ۳.۱ شکل op
```json
{ "op_id": "uuid-v4", "tenant_id": "…", "collection": "records",
  "kind": "upsert", "base_version": 12, "client_ts": "…",
  "payload_hash": "sha256", "sig": "HMAC(session_key)" }
```
`op_id` **از کلاینت** ولی `tenant_id`/`user_id`/`role` **از نشست** (پایان F‑06).

### ۳.۲ چرخهٔ اجرا
```
pending ──► sending ──► applied        (نتیجهٔ سرور ذخیره می‌شود)
   │           │
   │           ├─► rejected(reason)   → وضعیت «نیازمند تصمیم»، حفظ payload، بدون حذف
   │           └─► retry(n) با backoff نمایی + jitter، سقف تعریف‌شده
   └─► quarantined (پس از سقف) — دیده‌شدنی در UI، هرگز دور ریخته نمی‌شود
```
- **هیچ‌گاه** `slice(-500)` (باگ F‑07). سقف D‑27: ۲۰۰۰ op / ۳۰ روز؛ رسیدن به سقف ⇒ **توقف پذیرش جدید + هشدار**، نه حذف قدیمی.
- `applied_ops` سروری با `UNIQUE(tenant_id, op_id)`؛ تکرار ⇒ بازپخش همان نتیجه (idempotent).
- ترتیب: ردیف‌های هم‌مجموعه با `base_version`؛ عملیات مستقل موازی. عبور از ترتیب ⇒ `409 ordering`.
- ack فقط پس از commit سرور؛ ack گم‌شده ⇒ تکرار بی‌اثر.
- ابطال کاربر (D‑27): ترتیب قطعی = `W1` ← ثبت سفارش‌های صف ← `W2` ← (W3 در اتصال بعد).

### ۳.۳ بازیابی پس از کرش
- هر op تا قبل از `applied` در ذخیره‌گاه پایدار می‌ماند (نه در حافظه).
- راه‌اندازی مجدد: اسکن صف → ارسال مجدد با همان `op_id` → تطبیق نتیجه.
- device token/نشست در همان مخزن امن کلید؛ نشست منقضی ⇒ صف **حفظ** می‌شود ولی ارسال متوقف تا ورود مجدد.

## ۴. امنیت کش

| تهدید | کنترل |
|---|---|
| خواندن فایل کش از دیسک | AES‑GCM؛ کلید در OS keystore/DPAPI یا WebCrypto غیرقابل‌استخراج |
| کپی پایگاه به دستگاه دیگر | کلید به دستگاه گره خورده؛ داده بی‌مصرف |
| نشت پس از حذف کاربر | ابطال نشست ⇒ پاک‌سازی کش محلی در اولین اجرا |
| کش مستأجر دیگر | پیشوند `tenant_id` + تخلیهٔ کامل در تغییر مدرسه |
| عکس صفحه‌نمایش/دیباگر | خارج از دامنهٔ v1؛ در ۱۶ ریسک ثبت شد |
