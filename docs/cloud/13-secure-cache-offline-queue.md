## ۱. سه مخزن محلی، سه قاعدهٔ متفاوت

| مخزن | چیست | مرجع؟ | عمر | رمزنگاری |
|---|---|---|---|---|
| **Cache** | کپی خواندنی از اسکوپ کاربر | ❌ هرگز | `min(۷ روز, پایان نشست/ابطال)` | AES‑GCM با کلید غیرقابل‌استخراج |
| **Queue** | عملیات تأییدنشدهٔ کاربر | ❌ تا adjudication | تا تأیید/ابطال، **بدون حذف خودکار** | همان کلید (متن + متادیتا) |
| **Backup** | ۱۴ نسخهٔ روزانهٔ مدیر | ❌ | ۱۴ نسخهٔ چرخشی | همان کلید |

هیچ‌کدام «نسخهٔ دومِ حقیقت» نیستند. حقیقت = ردیف سرور با `tenant_id` (۱۲ §۴).

## ۲. چرخهٔ عمر کش (باگ F‑09/F‑07 در مقصد منتفی)

```
ورود موفق ──► ساخت کلید نشست (WebCrypto non-extractable)
             └─► کش فقط برای `tenant_id` فعال
هر پاسخ pull ──► upsert با `server_seq`
پایان نشست / ابطال / W1 ──► پاک‌سازی کش **قبل از** TTL  (قاعدهٔ ۰۳)
۷ روز گذشت ──► پاک‌سازی خودکار (فقط کش)
تغییر مدرسه ──► تخلیهٔ کامل (کش + صف + کلید)
```
- TTL بر پایهٔ `last_session_end` **و** `cached_at` محاسبه می‌شود؛ هرکدام زودتر.
- نشان `revoked_before(ts)` از سرور: هر ردیف با `server_seq` قدیمی‌تر از آن اعمال نمی‌شود.
- ابطال سمت سرور (W1) بی‌درنگ اعمال می‌شود حتی اگر دستگاه آفلاین باشد؛ در اولین اتصال اجرا می‌شود.

## ۳. صف عملیات — قرارداد مقصد

### ۳.۱ شکل op
```json
{ "op_id": "uuid-v4", "tenant_id": "…", "collection": "records",
  "kind": "upsert", "base_version": 12, "client_ts": "…",
  "payload_hash": "sha256", "sig": "HMAC(session_key)" }
```
`op_id` **از کلاینت** ولی `tenant_id`/`user_id`/`role` **از نشست** (پایان F‑06).

### ۳.۲ چرخهٔ اجرا — وضعیت‌ها

| وضعیت | معنا | چه‌کسی تغییرش می‌دهد | payload |
|---|---|---|---|
| `pending` | در انتظار ارسال (عادی) | خودکار | حفظ |
| `sending` | در حال ارسال | خودکار | حفظ |
| `applied` | سرور commit کرد | خودکار (پس از ack) | حفظ تا تأیید کاربر |
| `rejected` | سرور **رد قطعی** کرد (`4xx` منطقی) | خودکار | حفظ |
| `conflict` | تعارض ⇒ «نیازمند تصمیم» (D‑28) | انسان مجاز | حفظ |
| `retry_wait` | تلاش ناموفق موقت، در backoff | خودکار | حفظ |
| **`review`** | **عمر > ۳۰ روز (D‑27) — نیازمند بررسی انسانی** | انسان مجاز | **حفظ کامل** |
| **`quarantined`** | سقف تلاش تمام شد یا خطای نامشخص مکرر | خودکار ⇒ نیازمند بررسی | **حفظ کامل** |
| `ack_unknown` | ارسال رفت ولی ack نرسید؛ نتیجه نامعلوم | بازپخش idempotent | حفظ |
| `orphaned` | کاربر/دستگاه باطل شد و مالک صف از دست رفت | سیستم | حفظ (فقط‌خواندنی) |

```
pending ──► sending ──► applied
   │            ├─ 4xx منطقی ─► rejected(reason)
   │            ├─ 409 ─────────► conflict
   │            ├─ 5xx/شبکه ────► retry_wait ─► sending …
   │            └─ سقف تلاش ────► quarantined
   └─ (هر وضعیتِ باز، پس از ۳۰ روز) ─► review
```
- **هیچ‌گاه** `slice(-500)` (باگ F‑07). سقف D‑27: **۲۰۰۰ op برای هر دستگاه**؛ رسیدن به سقف ⇒ **توقف پذیرش جدید + هشدار** (۹۰٪ ⇒ هشدار نرم، ۱۰۰٪ ⇒ پذیرش متوقف)، نه حذف قدیمی.
- `applied_ops` سروری با `UNIQUE(tenant_id, op_id)`؛ تکرار ⇒ بازپخش همان نتیجه (idempotent).
- ترتیب: ردیف‌های هم‌مجموعه با `base_version`؛ عملیات مستقل موازی. عبور از ترتیب ⇒ `409 ordering`.
- ack فقط پس از commit سرور؛ ack گم‌شده ⇒ تکرار بی‌اثر (نه «موفق» فرض‌کردن).

### ۳.۲.۱ قاعدهٔ ۳۰ روز (D‑27) — صریح

| پرسش | پاسخ تعریف‌شده |
|---|---|
| op بعد از ۳۰ روز چه می‌شود؟ | وضعیتش **`review`** می‌شود؛ **حذف نمی‌شود**؛ **موفق هم اعلام نمی‌شود** |
| آیا خودکار ارسال می‌شود؟ | **نه** — تا تصمیم انسان (`approve` / `reject` / `edit`) در وضعیت `review` می‌ماند |
| payload چه می‌شود؟ | **کامل حفظ** می‌شود (همان بایت‌های اصلی + `payload_hash`)؛ فقط فشرده‌سازی ذخیره‌سازی مجاز است، نه تغییر محتوا |
| تفاوت `review` و `quarantined`؟ | `review` = «زمان گذشته»؛ `quarantined` = «تلاش‌ها/خطاها تمام شده». هر دو نیازمند انسان‌اند ولی دلیل و مسیر تصمیم متفاوت است |
| تفاوت با `rejected`؟ | `rejected` حکم **سرور** است؛ `review` حکم **انسان** است؛ `rejected` هم قابل بازبینی است ولی خودکار ارسال نمی‌شود |
| چه کسی می‌تواند تعیین تکلیف کند؟ | مالک همان ردیف، سرگروه، یا مدیر مدرسه (ماتریس ۰۷)؛ هر تصمیم در `audit` + `queue_decision(op_id, actor, action, reason, ts)` |
| آیا کاربر می‌تواند op را پاک کند؟ | فقط با `reject` ثبت‌شده (اثر «انصراف») — پاک‌سازی خام و بی‌سابقه ممنوع |
| آیا سقف ۲۰۰۰ عملیات شامل op‌های `review` است؟ | بله؛ ولی چون حذف ممنوع است، رسیدن به سقف ⇒ **بستن پذیرش جدید + بنر «نیازمند بررسی»** |

### ۳.۲.۲ ابطال دستگاه (D‑27 + W1/W2/W3)

ترتیب **قطعی** و غیرقابل‌جابه‌جایی:
1. `W1` — ابطال نشست/توکن سمت سرور (بی‌درنگ، مستقل از اتصال دستگاه).
2. **تعیین تکلیف صف:** هر op `pending`/`retry_wait`/`sending` ⇒ تلاش برای adjudication:
   - اگر نتیجه از سرور قابل بازیابی است (`applied_ops`) ⇒ همان نتیجه ثبت می‌شود.
   - اگر قابل بازیابی نیست ⇒ `ack_unknown` بماند و **UNKNOWN** علامت بخورد؛ هرگز `applied` فرض نمی‌شود.
3. `W2` — نابودی کلید محلی ⇒ کش و **payload صف** غیرقابل خواندن می‌شوند؛ اما **متادیتای op** (شناسه، زمان، هش payload، وضعیت) روی سرور می‌ماند تا سرنوشت هر عملیات قابل حسابرسی باشد.
4. `W3` — حذف فیزیکی فایل‌های محلی فقط پس از اتصال بعدی؛ برای دستگاهی که هرگز وصل نمی‌شود، W3 **تضمین نمی‌شود** (ریسک ثبت‌شده در ۱۰).

قاعدهٔ طلایی: **هیچ عملیات نامعلومی در هیچ مرحله‌ای `ACK` یا «موفق» اعلام نمی‌شود.** وضعیت‌های `UNKNOWN`/`ORPHANED` در گزارش وضعیت مدرسه دیده می‌شوند.

### ۳.۳ بازیابی پس از کرش
- هر op تا قبل از `applied` در ذخیره‌گاه پایدار می‌ماند (نه در حافظه).
- راه‌اندازی مجدد: اسکن صف → ارسال مجدد با همان `op_id` → تطبیق نتیجه.
- device token/نشست در همان مخزن امن کلید؛ نشست منقضی ⇒ صف **حفظ** می‌شود ولی ارسال متوقف تا ورود مجدد.

## ۴. امنیت کش

| تهدید | کنترل |
|---|---|
| خواندن فایل کش از دیسک | AES‑GCM؛ کلید در OS keystore/DPAPI یا WebCrypto غیرقابل‌استخراج |
| کپی پایگاه به دستگاه دیگر | کلید به دستگاه گره خورده؛ داده بی‌مصرف |
| نشت پس از حذف کاربر | ابطال نشست ⇒ پاک‌سازی کش محلی در اولین اجرا |
| کش مستأجر دیگر | پیشوند `tenant_id` + تخلیهٔ کامل در تغییر مدرسه |
| عکس صفحه‌نمایش/دیباگر | خارج از دامنهٔ v1؛ در ۱۶ ریسک ثبت شد |
