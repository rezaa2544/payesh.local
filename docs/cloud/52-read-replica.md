# ردیف ۵۲ — replica فقط‌خواندنی برای pull و سیاست read-your-writes

**وضعیت:** Done (تصمیم داده‌محور + ناوردا اثبات‌شده). ساخت replica واقعی = **OWNER** (وابسته به ۵۶).
**شاهد خام:** [`reports/evidence/read-policy-52.txt`](reports/evidence/read-policy-52.txt) —
بازتولید: `bash docs/cloud/reports/evidence/run-52-read-policy.sh`

## تصمیم: replica ساخته نمی‌شود (فعلاً)

معیار پذیرش این ردیف مشروط است: «فقط اگر تست بار نشان دهد خواندن گلوگاه است».
شاهد ردیف ۴۶ (`docs/cloud/46-fleet-load.md`) این شرط را رد می‌کند:

| کلاینت | RPS | pull p99 | push p99 | نتیجه |
|---|---|---|---|---|
| ۳۰۰ (سقف سالم) | 268 | 1323ms | 1406ms | خواندن **ارزان‌تر** از نوشتن |
| ۶۰۰ | 244 | 3437ms | 3578ms | هر دو با هم می‌شکنند |

RPS در همهٔ پله‌ها ~۲۵۰ ماند و علت، اندازهٔ pool و ظرفیت DB بود (ردیف ۴۵: `db_connections=4`،
سقف pool). یعنی **گلوگاه خواندن نیست**؛ replica هزینهٔ سازگاری می‌آورد بی‌آنکه RPS را بالا ببرد.

شرط بازبینی (عدد دارد، در کد: `replica-policy.POLICY.revisit_when`):

- `pull_p99 / push_p99 > 1.3` در بار پایدار ≥ ۳۰۰ کلاینت، یا
- سهم CPU خواندن روی primary > ۶۰٪.

تا آن زمان: همهٔ خواندن‌ها روی primary — صریح در پاسخ API (`read_from: "primary"`).

## ناوردا: دستگاه نوشته‌های خودش را همیشه می‌بیند

این بخش مستقل از تصمیم بالا اجرا شد، چون روزی که replica اضافه شود همین‌جا شکسته می‌شود.

`server/replica-policy.js` تنها جای تصمیم است:

| حالت | مقصد | دلیل |
|---|---|---|
| replica تنظیم نشده | primary | `no_replica_configured` |
| replica تازه (تأخیر ≤ ۲۰۰۰ms) و نوشتهٔ دستگاه را دیده | replica | `replica_fresh` |
| دستگاه نوشته‌ای دارد که replica ندیده (`own_seq > replica_seq`) | **primary** | `read_your_writes` |
| تأخیر نامعلوم (replica پاسخ نمی‌دهد/خطا) | **primary** | `lag_unknown` |
| تأخیر > ۲۰۰۰ms | **primary** | `lag_over_budget` |

اتصال به Gateway: `PAYESH_PG_REPLICA_URL` (اختیاری). بدون آن هیچ pool دومی ساخته نمی‌شود.
هنگام push، بزرگ‌ترین `seq` همان دستگاه ثبت می‌شود (`tenancy.maxFeedSeq` → `noteOwnWrite`)، و pull
با همان عدد مقصد را انتخاب می‌کند. پاسخ pull همیشه `read_from` و `read_reason` را می‌گوید.

## اندازه‌گیری (واقعی، نه شبیه‌سازی)

۴۰ دستگاه × ۵ دور؛ هر دستگاه push می‌کند و **بلافاصله** pull:

| سنجه | مقدار |
|---|---|
| push / pull موفق | ۲۰۰ / ۲۰۰ |
| خواندن کهنهٔ نوشتهٔ خودِ دستگاه | **۰** |
| خطا | ۰ |
| مقصد خواندن | `primary` ۲۰۰/۲۰۰ |
| سلامت پس از بار | `/healthz 200` · `/readyz 200` |
| رگرسیون | `۹۶ موفق · ۰ ناموفق` |

آزمون سیاست: `npm run test:replica52` → `RP-01..RP-09`، ۹/۹ (شامل کنترل منفی: replica عقب
می‌ماند ⇒ primary؛ تأخیر نامعلوم ⇒ primary).

## آنچه ادعا نمی‌شود

- **replica واقعی وجود ندارد**؛ مسیر `replica_fresh` با دادهٔ واقعی سنجیده نشده، فقط منطق
  تصمیم و برگشت کامل به primary. ساخت replica = تصمیم و هزینهٔ OWNER (ردیف ۵۶).
- سنجش تأخیر در همان لحظهٔ درخواست انجام می‌شود (دو کوئری سبک)؛ زیر بار بسیار سنگین خودش
  هزینه دارد و باید با کش کوتاه (۱–۲ ثانیه) در استقرار واقعی پوشش داده شود.
