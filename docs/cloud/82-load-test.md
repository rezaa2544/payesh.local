# ردیف ۸۲: آزمون بار و اندازه‌گیری — مسیر مستقیم (RPC + RLS) و Gateway روی PostgreSQL

> تاریخ: ۱۴۰۵/۰۸/۲۰ (2026-11-11) · مجری: ARENA (ابزار + CI) · OWNER: اجرا روی دیتابیس مدیریت‌شده (T2)

## ۱. قانون برچسب‌گذاری

- **[S]**: شبیه‌سازی روی ماشین توسعه یا runner CI (loopback، دستگاه‌های مصنوعی). **همهٔ** اعداد این ردیف [S] هستند.
- برچسب سنجیده‌شده روی **هدف واقعی** (دیتابیس مدیریت‌شدهٔ مالک، T2) فقط با `PAYESH_T2_MANAGED_DB=1` پذیرفته می‌شود. این کار فقط از OWNER برمی‌آید و CI هرگز آن را تنظیم نمی‌کند. ابزار بدون آن با کد خروج ۲ رد می‌کند (LD-02).
- **ادعای «نامحدود» ممنوع است.** گزارشی که این واژه یا معادل‌هایش را داشته باشد رد می‌شود (`claimsGate`، LD-02). عددهای این سند فقط همین اجرا را توصیف می‌کنند، نه ظرفیت تولید را.

## ۲. ابزار

| بخش | فایل |

| آزمون و دروازه | `tests/load-82.js` (`npm run test:load82`) |

هر دستگاه مجازی token، `X-Device-Id` و مکان‌نمای pull (`since_seq`) خودش را دارد. ترکیب درخواست‌ها ۸۰٪ pull و ۲۰٪ push است (۱ تا ۳ op). بار به‌صورت closed-loop با N کارگر هم‌زمان روی اتصال keep-alive فرستاده می‌شود. حافظهٔ RSS فرایند Gateway هر ثانیه از `/proc/<pid>/status` نمونه‌برداری می‌شود.

| برچسب و ادعا | همهٔ بخش‌ها برچسب دارند و هیچ ادعای نامحدودی نیست |

## ۴. نتیجهٔ اجرای اصلی [S]

پیکربندی: ۲٬۰۰۰ دستگاه، ۲۰ مدرسه، ۶۴ هم‌زمان، ۳۰ ثانیه پس از ۵ ثانیه گرم‌کردن. اعداد دقیق در `docs/cloud/reports/evidence/load-82.txt` و گزارش خام `load-82-report.json` آمده‌اند:

- [S] در سه اجرای محلی، ۱۷ تا ۱۹ هزار درخواست با ۵۷۰ تا ۶۲۰ درخواست در ثانیه.
- [S] تأخیر p50 بین ۱۰۰ و ۱۱۰، p95 بین ۱۲۶ و ۱۴۷، و p99 بین ۱۴۲ و ۱۷۷ ms.
- [S] صفر خطا.
- [S] RSS از حدود ۸۲ به ۸۷ MB رسید (رشد ۳ تا ۵ MB)، بدون نشانهٔ نشت.

این عددها روی **یک** فرایند Gateway و PostgreSQL محلیِ کوچک (embedded، `shared_buffers=16MB`) به دست آمده‌اند. روی runner CI با `postgres:16` عددها متفاوت‌اند و هر اجرا گزارش خام خودش را دارد.

## ۵. کنترل‌های منفی (روی فرایند واقعی Gateway)

| تزریق | دروازهٔ قرمزشده |
|---|---|
| نگه‌داشتن ۶۴ KB به‌ازای هر درخواست (نشت) | memory_leak |
| `PAYESH_FEATURE_KILL=push` (پاسخ 503) | error_rate |
| تأخیر ۱٫۲ ثانیه پیش از هر درخواست | p95 |
| ادعای «unlimited» یا «نامحدود»، نبود برچسب، برچسب هدف واقعی بدون دیتابیس مدیریت‌شده | claims |

LD-08 کنترل مثبت است: همان پروفایل کوتاه روی Gateway دست‌نخورده سبز می‌ماند. پس قرمز شدن کنترل‌های منفی از تزریق است، نه از خود پروفایل.

## ۶. اجرای OWNER روی T2 (خارج از ARENA)

```
PAYESH_T2_MANAGED_DB=1 node tools/load-82.mjs --base https://<gateway> --secret "$GW_SECRET" \
  --gw-pid <pid روی میزبان Gateway> --devices 2000 --tenants 20 --duration 300 --concurrency 64 \
  --label M --out load-82-T2.json
```

فقط خروجی همین اجرا روی دیتابیس مدیریت‌شده برچسب هدف واقعی می‌گیرد. حذف `--gw-pid` اندازه‌گیری حافظه را خاموش می‌کند و این موضوع در گزارش ثبت می‌شود.

## ۷. مسیر مستقیم (هدف اصلی ردیف؛ ADR‑105، Proposed)

معیار پذیرش این ردیف می‌گوید هدف اصلی **مسیر مستقیم** است: توابع RPC و RLS روی PostgreSQL، نه Gateway. بخش‌های ۲ تا ۶ نسخهٔ Gateway را پوشش می‌دهند. این بخش مسیر مستقیم را پوشش می‌دهد.

### ۷.۱ ابزار

| بخش | فایل |
|---|---|
| اسکریپت بار مسیر مستقیم | `tools/load-82-direct.mjs` |
| آزمون و دروازه (LDD-01..10) | `tests/load-82-direct.js` (`npm run test:load82direct`) |
| CI | `api-contract.yml`، گام «Load test, direct path (row 82)» روی `postgres:16` با `LOAD82D_REQUIRE_PG=1` و گزارش خام `load-82-direct-report.json` |
| یافته و اصلاح | `db/migrations/direct/0006_direct_rls_initplan.up.sql` (+ down) |

- هر فراخوانی دقیقاً همان کاری را می‌کند که PostgREST برای یک `/rpc` انجام می‌دهد: یک تراکنش روی اتصالِ pool، شامل `SET LOCAL ROLE payesh_direct_client`، ادعاهای تأییدشدهٔ توکن در `request.jwt.claims`، فراخوانی `sync_pull` یا `sync_push`، و سپس `COMMIT`.
- نقش ورود `payesh_ld82_api` فقط عضو `payesh_direct_client` است و BYPASSRLS ندارد. اندازهٔ pool ثابت و برابر ۳۲ است.
- ۲٬۰۰۰ دستگاه در ۲۰ مدرسه تعریف می‌شوند. هر مدرسه با `bootstrap_school` و کلیدهای دامنهٔ منتشرشده (ردیف ۱۰۷) ساخته می‌شود. هر دستگاه با `enroll_device` و `register_device_key` (ردیف ۱۰۶) ثبت می‌شود.
- هر رکورد ارسالی در سمت دستگاه با `tools/e2e1.js` رمز سرتاسری می‌شود.
- ترکیب درخواست‌ها ۸۰٪ pull و ۲۰٪ push است. هر دستگاه فقط رکوردهای خودش را و فقط روی نسخه‌ای که دیده می‌نویسد.
- تأخیرِ پرش HTTP ارائه‌دهنده در این عددها نیست. اندازه‌گیری آن با OWNER و روی T2 است (۷.۵).

### ۷.۲ دروازه‌ها

آستانهٔ نرخ خطا (۰٫۵٪) و p95 (۱۰۰۰ ms) همان آستانه‌های SLO هستند. دروازه‌های ویژهٔ مسیر مستقیم این‌ها هستند:

| دروازه | قرمز وقتی |
|---|---|
| یکپارچگی op | هر op از نوع stale، conflict، rejected یا duplicate، یا وقتی تعداد رکوردهای جدید در DB با تعداد اعمال‌شده برابر نیست |
| نشت نشست | پس از اجرا نشستی از نقش API در حالت `idle in transaction` بماند، یا اوج نشست‌ها از pool بیشتر شود. مسیر مستقیم فرایند برنامه ندارد، پس دروازهٔ نشت روی نشست‌های DB است |
| جداسازی مدرسه زیر بار (RLS) | دستگاه مدرسهٔ A حتی یک رکورد از مدرسهٔ دیگر ببیند، یا همهٔ رکوردهای A را نبیند |
| برچسب و ادعا | مانند Gateway: همه چیز [S] و بدون ادعای نامحدود. برچسب هدف واقعی بدون `PAYESH_T2_MANAGED_DB=1` رد می‌شود |

### ۷.۳ یافته: هزینهٔ RLS به‌ازای هر سطر، در کل پایگاه داده

اجرای اول [S] روی مهاجرت‌ها تا 0005 دروازهٔ p95 را قرمز کرد.

- **علت:**
  - سیاست‌های `record` برای **هر سطر بررسی‌شده** `can_access(...)` را صدا می‌زدند.
  - هر فراخوانی `can_access` خودش `current_user_id()` را اجرا می‌کرد: تجزیهٔ claims، یک join، و SECURITY DEFINER با search_path ثابت که هرگز inline نمی‌شود. هزینه حدود ۰٫۲۵ ms برای هر سطر بود.
  - سیاست‌ها گزارهٔ مدرسه نداشتند. پس پیمایش feed یک مدرسه، سطرهای همهٔ مدرسه‌های دیگر را هم از این تابع رد می‌کرد.
  - در نتیجه تأخیر با **کل پایگاه داده** رشد می‌کرد، نه با اندازهٔ مدرسه.
- **اصلاح** (`0006_direct_rls_initplan`، با همان معنا):
  - توابعِ وابسته به فراخوان به شکل `(SELECT fn())` نوشته شدند. PostgreSQL آن‌ها را یک بار برای هر دستور (InitPlan) اجرا می‌کند، نه یک بار برای هر سطر.
  - سیاست‌های `record` اول `tenant_id = مدرسهٔ فراخوان` را می‌خواهند. حالا ایندکس `record_feed_idx (tenant_id, seq)` شرط ایندکس می‌شود.
  - مدیرِ همان مدرسه بدون جست‌وجوی قابلیت در هر سطر رد می‌شود. بقیه همچنان از `can_access` (قابلیت بر اساس کلاس، دانش‌آموز یا مجموعه) عبور می‌کنند.
- **هم‌معنایی:**
  - `rls-pentest-109` (۱۰۰ حمله و ۲۵ جهش) و `direct-sync-108` روی 0006 سبزند. CI هر دو را روی 0006 اجرا می‌کند.
  - جهش «RLS رکورد» در pentest از 0006 به بعد هر دو لایه را برمی‌گرداند.
- **دفاع لایه‌ای (LDD-10):** حتی اگر `can_access` همیشه true برگرداند، دستگاه مدرسهٔ B هیچ رکوردی از A نمی‌بیند، چون گزارهٔ مدرسه در خود سیاست است.
- **LDD-09:** طرح اجرای پرس‌وجوی feed را بررسی می‌کند. روی head شرط ایندکس `tenant_id = $InitPlan` دیده می‌شود. با برگرداندن 0006 دوباره فیلتر `can_access` برای هر سطر برمی‌گردد.

### ۷.۴ نتیجه [S] (پروفایل یکسان: ۲٬۰۰۰ دستگاه، ۲۰ مدرسه، ۶۴ هم‌زمان، pool ۳۲، ۳۰ ثانیه + ۵ ثانیه گرم‌کردن)

عددهای دقیق در `docs/cloud/reports/evidence/load-82-direct.txt` و گزارش خام `load-82-direct-report.json` آمده‌اند. ماشین ۲ vCPU داشت و مولد بار و پایگاه داده روی همان ماشین بودند.

| | پیش از اصلاح (تا 0005) | پس از اصلاح (0006) |
|---|---|---|
| [S] فراخوانی در ثانیه | ۲۷ | ۳۰۹ تا ۳۱۸ (چند اجرا) |
| [S] p50 / p95 / p99 (ms) | ۲۱۸۲ / ۳۷۹۷ / ۴۰۸۰ | p50 حدود ۱۹۵، p95 بین ۳۰۰ و ۳۱۳، p99 بین ۳۶۹ و ۳۸۴ |
| [S] خطا | ۰ | ۰ |
| [S] یکپارچگی op، جداسازی، نشست | سبز | سبز (stale/conflict/rejected = ۰، رکوردها برابر، foreign = ۰، idle-in-tx = ۰) |
| دروازه | قرمز (p95) | سبز |

کنترل‌های منفی روی همان پایگاه دادهٔ زنده اجرا می‌شوند و هر تزریق پس از اجرا برگردانده می‌شود:

| تزریق | دروازهٔ قرمزشده |
|---|---|
| طرح ۵ op در دقیقه برای هر مدرسه (`54000`) | error_rate (LDD-04) |
| trigger با `pg_sleep(1.2)` روی `record` | p95 (LDD-05) |
| تراکنشی که نقش API باز رها کرده | session_leak (LDD-06) |
| جهش `record_read USING (true)` | isolation (LDD-07) |

LDD-08 کنترل مثبت است: پس از برگرداندن همهٔ تزریق‌ها، همان پروفایل کوتاه سبز می‌ماند.

### ۷.۵ اجرای OWNER روی T2 (خارج از ARENA)

برای بار مستقیم روی پایگاه دادهٔ مدیریت‌شده، رشتهٔ اتصال **مدیر** فقط در متغیر محیطی و فقط روی ماشین مالک قرار می‌گیرد، هرگز در مخزن:

```
PAYESH_T2_MANAGED_DB=1 PAYESH_PG_ADMIN='<رشتهٔ اتصال مدیر T2>' \
  node tools/load-82-direct.mjs --devices 2000 --tenants 20 --duration 300 --concurrency 64 --pool 32 \
  --label M --out load-82-direct-T2.json
```

ابزار یک پایگاه دادهٔ جدا (`payesh_ld82d_*`) می‌سازد و پس از اجرا حذفش می‌کند. اگر ارائه‌دهنده ساختن پایگاه داده را اجازه ندهد، اجرا روی یک پروژهٔ آزمایشی جدا انجام می‌شود، نه روی پروژهٔ تولید. اندازه‌گیری پرش HTTP (PostgREST ارائه‌دهنده) هم بخشی از همین اجرای OWNER است.
