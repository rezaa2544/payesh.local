`docs/cloud/reports/evidence/outbox-40.txt` (بازتولید: `bash docs/cloud/reports/evidence/run-40-outbox.sh`).
**دامنه:** صف عملیات سمت دستگاه (مرورگر/WebView) + هم‌سویی با همان `server/sync.js` تولیدی.

> وضعیت امنیتی پروژه با این ردیف تغییر نمی‌کند و همچنان **UNKNOWN** است.

## ۱) مشکلی که بسته شد (ریسک E‑14‑2 در `docs/cloud/16`)

صف کلاینت در `localStorage` بود و در `saveQueue()` با برشِ «۵۰۰ عملیات آخر» ذخیره می‌شد.
نتیجه: اگر کاربر آفلاین بیش از ۵۰۰ تغییر می‌ساخت، **کهنه‌ترین عملیات بی‌صدا حذف می‌شد**؛
و اگر برنامه وسط ارسال بسته می‌شد، هیچ نشانه‌ای از آنچه فرستاده شده بود نمی‌ماند
(ارسال دوباره یا گم‌شدن، هر دو ممکن بود).

## ۲) قرارداد جدید

| موضوع | مقدار/رفتار | منبع |
|---|---|---|
| محل ذخیره | IndexedDB (object store `ops`، ایندکس‌های `state`/`seq`) | `client/outbox-web.js` |
| سقف صف | `capacity = 5000` عملیات فعال | `DEFAULTS.capacity` |
| رفتار پر شدن | خطای صریح `queue_full`؛ عملیات تازه پذیرفته **نمی‌شود**؛ هیچ عملیات قبلی حذف نمی‌شود؛ `stats.full = true` و توست به کاربر | `enqueue()` / `enqueueOp()` |
| ترتیب ارسال | صعودی بر `seq` (FIFO) | `claim()` |
| اجارهٔ ارسال | `leaseMs = 30000`؛ عملیات در حال ارسال `inflight` با `lease_until` | `claim()` |
| حذف | فقط بعد از تصمیم سرور (`ack` پس از `applied`/`rejected`/`conflict`) | `ack()` / `drain()` |
| شکست موقت | عقب‌نشینی نمایی: `base 1s × 2^(n-1)` تا سقف ۵ دقیقه | `fail()` |
| شکست دائمی | بعد از `maxAttempts = 6` → `blocked`؛ **حذف نمی‌شود**، در `stats.blocked` دیده می‌شود و `retry()` دارد | `fail()` / `retry()` |
| کلید idempotency | `k` پایدار روی خود عملیات؛ در همهٔ تلاش‌ها و پس از restart همان می‌ماند و به‌عنوان `uid` به سرور می‌رود | `enqueue()` / `toWire()` |
| بازیابی پس از restart | `recover()` اجاره‌های منقضی را به `pending` برمی‌گرداند؛ `outboxInstance()` در `app.js` عملیاتِ مانده را دوباره در نمای صف می‌گذارد | `recover()` |

**چرا «اعمال دقیقاً یک‌بار» درست است؟** سرور برای هر عملیات `uid` را در `sync_seen` نگه می‌دارد
(`server/sync.js` → `store.syncSeen(uid)` → `duplicate: true`) و در سطح درخواست هم
`idempotency_key` را تکرار می‌کند (`idemRemember`). پس ارسال دوبارهٔ همان `k` هیچ ردیف
تکراری نمی‌سازد — این را آزمون OB‑11 روی همان تابع تولیدی سرور ثابت می‌کند، نه روی شبیه‌سازی.

## ۳) جریان ارسال (drain)

```
enqueue → pending ──claim──▶ inflight(lease) ──send──▶ سرور
                                   │                      │
                     lease expired │                      ├─ applied  → ack (حذف)
                 (crash/restart)   ▼                      ├─ rejected → onRejected + ack (فهرست بررسی)
                                 pending ◀──fail──────────┴─ conflict → onConflict + ack
                                   │
                          attempts ≥ 6 → blocked (بازگشت دستی با retry)
```

`app.js` همین گام‌ها را در `flushQueue()` صدا می‌زند: `recover()` → `markInflight(batch)` →
ارسال → `ackMany(settled)` یا `failMany(...)`. عملیاتی که سرور درباره‌اش تصمیم نداده
(`no_verdict`) حذف نمی‌شود و با backoff برمی‌گردد.

## ۴) آزمون‌ها (OB‑01..OB‑15، همه سبز)

```bash
node --experimental-sqlite --disable-warning=ExperimentalWarning tests/outbox-40.js   # → OUTBOX-40-OK
```

| شناسه | ادعا |
|---|---|
| OB-01 | باز شدن store و ایندکس‌ها؛ سقف پیش‌فرض ۵۰۰۰ |
| OB-02 | ماندگاری پس از restart با همان کلید |
| OB-03 | افزودن تکراری با همان کلید، رکورد دوم نمی‌سازد |
| OB-04 | سقف صف: `queue_full`، عملیات قبلی دست‌نخورده، `stats.full`، رویداد ثبت‌شده |
| OB-05 | دو برداشت هم‌زمان (دو تب) یک عملیات را دوباره نمی‌دهد |
| OB-06 | crash وسط ارسال: اجاره فعال مانع برداشت زودهنگام؛ بعد از انقضا همان عملیات با همان کلید برمی‌گردد |
| OB-07 | backoff نمایی و پذیرش دقیقاً در `next_at` |
| OB-08 | بعد از سقف تلاش → `blocked` و **حذف نمی‌شود** |
| OB-09 | `retry()` روی blocked → ارسال موفق |
| OB-10 | ۴۰ عملیات روی **سرور واقعی** اعمال و صف خالی |
| OB-11 | ارسال دوباره پس از crash: سرور ۰ ردیف تکراری می‌سازد (اعمال دقیقاً یک‌بار) |
| OB-12 | قطعی کامل شبکه: ۱۰۰ عملیات می‌مانند، هیچ‌کدام گم نمی‌شود |
| OB-13 | ردِ سرور: از صف خارج و در فهرست بررسی ثبت می‌شود (بدون حذف خاموش) |
| OB-14 | تعارض: از صف خارج و در فهرست تصمیم‌گیری ثبت می‌شود |
| OB-15 | سیم‌کشی واقعی: `app.js` صندوقچه را صدا می‌زند، حذف خاموش حذف شده، `index.html` اسکریپت را بار می‌کند |

آزمون‌های منفی (همان‌طور که در جدول دیده می‌شود): پر شدن سقف، شکست شبکه، crash وسط ارسال،
رد و تعارض سرور. هیچ‌کدام به «حذف خاموش» یا «اعمال دوباره» منتهی نمی‌شوند.

## ۵) آنچه تغییر نکرده

* قرارداد Sync v1 و `server/sync.js` دست‌نخورده‌اند (همان `uid`/`idempotency_key` که از قبل بود).
* `server/sync.js` هیچ مسیر جدیدی نگرفت؛ فقط کلاینت صفِ خودش را ماندگار کرد.
* `tests/run.js` و دروازهٔ شاهد آن دست‌نخورده‌اند (۹۶/۰ سبز)؛ این ردیف شاهد مستقل دارد.
* آینهٔ `localStorage` به‌عنوان **کش** مانده است تا نصب‌های قبلی بی‌دردسر ارتقا یابند؛
  اگر جا نشود، کش دور ریخته می‌شود، نه عملیات (منبع حقیقت صندوقچهٔ IndexedDB است).
* هیچ ارائه‌دهندهٔ پولی درگیر نشد؛ وضعیت امنیت **UNKNOWN**.
