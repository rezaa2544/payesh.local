# ردیف ۵۸ — Pager/On-call واقعی: کانال هشدار و ران‌بوک

**وضعیت:** کانال واقعی ساخته و **یک هشدار آزمایشی واقعاً ارسال و ثبت شد**
(`docs/cloud/reports/evidence/pager-58-real-alert.json`، message_id=92).
قسمت پایانی AC — «یک نفر on-call مشخص» — یک تصمیم مالک است (نام + شیفت) که در همین
سند در جدول on-call پر می‌شود.

## ۱) معماری کانال

```
رویداد (سلامت/همگام‌سازی/امنیت)  →  server/alerts.js: notify({...})
                                      ├─ یکسان‌سازی (۵ دقیقه با کلید)
                                      ├─ دفتر حسابرسی: alerts-audit/alerts.jsonl (همه رویدادها)
                                      └─ تلگرام Bot API (با بازگشت ۲×، ۵xx → تلاش مجدد، ۴xx → خاتمه)
```

توکن و chat از محیط خوانده می‌شوند (`PAYESH_ALERT_TELEGRAM_TOKEN`، `PAYESH_ALERT_CHAT`،
اختیاری: `PAYESH_ALERT_PROXY` برای شبکه‌های محدودشده). هیچ رازی در مخزن نیست.

سطح‌بندی با معیارهای توقف پایلوت (ردیف ۵۱): `S1` بحرانی، `S2` مهم، `S3` هشدار، `S4` اطلاع.

## ۲) راه‌اندازی (۳ دقیقه)

۱. یک بات بسازید: تلگرام → @BotFather → `/newbot` → توکن را در `PAYESH_ALERT_TELEGRAM_TOKEN`
   قرار دهید. (**بات موجود پروژه: @payesh_school_bot — در صورت استفادهٔ مجدد،
   `PAYESH_ALERT_CHAT` را برابر شناسهٔ چت دریافت‌کننده بگذارید.**)
۲. شناسهٔ چت: دریافت‌کننده یک‌بار `/start` را به بات بفرستد؛ شناسه از @userinfobot یا
   پاسخ WebHook به‌دست می‌آید.
۳. در صورت نیاز به پراکسی: `PAYESH_ALERT_PROXY=http://host:port`.

## ۳) آزمون واحد

`npm run test:alerts` (افزوده شد) → `AL checks=18 pass=18 fail=0` / `ALERTS-58-OK`.
شامل کنترل‌های منفی: بازگشت روی ۵xx، قطع شبکه، یکسان‌سازی، نبود توکن، اثبات اینکه
توکن هرگز در حسابرسی نمی‌نشیند (AL-07)، و سیم‌کشی مستقیم قواعد ردیف ۴۹ (`tools/alerts-49.mjs`)
به `server/alerts.js:notify()` (AL-08).

## ۴) شاهد واقعی

ارسال دستی از کد محصول:

```
PAYESH_ALERT_TELEGRAM_TOKEN=… PAYESH_ALERT_CHAT=… node server/alerts.js test
→ {"ok":true,"sent":true,"attempt":1,"message_id":92,"date":1794092352}
→ حسابرسی: ts=2026-11-07T22:59:14.631Z level=S4 key=manual-test sent=true message_id=92
```

**پاسخ API تلگرام** نشان می‌دهد پیام پذیرفته شده و یک `message_id` واقعی گرفته است.
این «پذیرش در سمت سرور تلگرام» است؛ ثبت `message_id` + دریافت‌کنندهٔ مشخص، قابل
حسابرسی است. اگر مالک بخواهد، می‌توان با افزودن یک دکمهٔ «تأیید دریافت» (inline button)
این شکاف را بست.

## ۵) جدول on-call (مالک پر می‌کند)

| نام | نقش | شیفت | کانال | یو‌سی |
|---|---|---|---|---|
| (مثلاً رضا احمدی) | مالک/اولین پاسخگو | همیشه (P0) | تلگرام @payesh_school_bot | — |

## ۶) سیاست صعود (Escalation)

- `S1` (بحرانی): ارسال فوری + بازنویسی در ۱ دقیقه اگر پاسخ نرسد (دستور `send` با کلید یکسان →
  محدود شده، برای صعود از کلید `esc:<event>` استفاده کنید).
- `S2`: ارسال + تکرار هر ۱۵ دقیقه تا ۳ بار.
- `S3/S4`: ثبت حسابرسی + ارسال یک‌بار.

## ۷) ماندنی‌ها

- قواعد «چه چیزی، کِی» به‌عنوان هشدار ارسال شود متعلق به ردیف ۴۹ است (healthz/metrics)؛
  `notify()` نقطهٔ وصل است.
- این کانال «ارسال» است، نه «تأیید دریافت از انسان»؛ اگر AC بعدی دریافت در گوشی را
  لازم داشت، یک دکمهٔ تأیید دریافت (callback) اضافه می‌شود.
