## چه چیزی ساخته شد

همه‌چیز فقط با SQL استاندارد PostgreSQL 13 به بالا نوشته شده است: بدون extension، بدون اسکیمای `auth.*` و بدون نقش‌های مخصوص ارائه‌دهنده. آزمون DI‑02 این را بررسی می‌کند.

### جدول‌ها (اسکیمای `payesh_direct`)

| جدول | محتوا | دسترسی کلاینت |
|---|---|---|
| `app_user` | `tenant_id`، `user_code` (کد کاربر در مدرسه)، `auth_subject` (شناسهٔ کاربر نزد سرویس Auth)، `role`، `disabled`، `revoked_at` | فقط SELECT: ردیف خود کاربر. مدیر همهٔ کاربران مدرسهٔ خودش را می‌بیند. |
| `device` | دستگاه‌های ثبت‌شدهٔ هر کاربر و `revoked_at` | فقط SELECT: دستگاه‌های خود کاربر. مدیر همهٔ دستگاه‌های مدرسه را می‌بیند. |
| `capability` | `action` (read/write) × `scope_kind` (school/class/student) × `scope_id`، و `collection` اختیاری | فقط SELECT: قابلیت‌های خود کاربر. مدیر همه را می‌بیند. |
| `identity_audit` | ردپای افزایشی هر تغییر هویت | فقط SELECT و فقط برای مدیر مدرسه |
| `record` | دادهٔ مدرسه برای مسیر مستقیم. فقط فرادادهٔ مسیریابی آشکار است. ردیف ۱۰۷ `payload` را به متن رمزشده سمت دستگاه تبدیل می‌کند. | SELECT/INSERT/UPDATE زیر RLS. بدون DELETE؛ حذف با tombstone `deleted_at` انجام می‌شود. |

مثال قابلیت‌ها:

- `('write', 'class', 7, 'attendance')` یعنی ثبت حضور برای کلاس ۷.
- `('read', 'student', 42, NULL)` یعنی دیدن همهٔ دادهٔ فرزند ۴۲.

نقش `manager` در مدرسهٔ خودش همه‌چیز را می‌بیند. هر نقش دیگری فقط چیزی را می‌بیند که قابلیتش اجازه می‌دهد. نقش بدون قابلیت صفر ردیف می‌بیند.

### نقش‌ها

| نقش | تعریف | کاربرد |
|---|---|---|
| `payesh_direct_owner` | NOLOGIN، NOBYPASSRLS | مالک جدول‌ها و توابع |
| `payesh_direct_client` | NOLOGIN، NOBYPASSRLS | نقش گروهی. نقش درخواست ارائه‌دهنده (مثلاً نقش «authenticated» در API) هنگام استقرار عضو آن می‌شود. هیچ کلاینتی کلید سرویس یا اعتبارنامهٔ مدیر دیتابیس ندارد (ADR §۲). |

### درز ارائه‌دهنده (تنها بخش قابل‌تعویض)

`payesh_direct.auth_subject()` و `payesh_direct.request_device_id()` ادعاهای توکنِ **تأییدشده** را از GUC تراکنشی `request.jwt.claims` می‌خوانند. این همان روشی است که لایهٔ API به سبک PostgREST به کار می‌برد.

برای ارائه‌دهندهٔ دیگر فقط همین دو تابع عوض می‌شوند. هر سه پیش‌شرط زیر جزو قرارداد استقرار است و ردیف ۱۰۹ آن‌ها را آزمون نفوذ می‌کند:

1. توکن باید ادعای `device_id` داشته باشد. ارائه‌دهنده آن را با hook توکن اضافه می‌کند (ردیف ۱۱۰).
2. کلاینت نباید بتواند SQL خام اجرا کند. فقط API جدول‌ها و RPCها در دسترس باشد. در غیر این صورت کلاینت می‌تواند `set_config` را صدا بزند.
3. نقش درخواست نباید BYPASSRLS باشد.

## قواعدی که داخل دیتابیس اعمال می‌شوند

1. **ادعای کلاینت اعتماد نمی‌شود.** نقش، مدرسه و قابلیت فقط از جدول‌ها خوانده می‌شوند. اگر توکن ادعای `role:'manager'` یا `tenant_id` مدرسهٔ دیگر داشته باشد، دامنهٔ دید تغییر نمی‌کند (DI‑08).
2. **ابطال.** کاربر `disabled`، کاربر `revoked`، دستگاه باطل‌شده، دستگاه کاربر دیگر، دستگاه ناشناخته و نبود ادعای دستگاه همگی به «بدون هویت» می‌رسند. در این حالت همهٔ سیاست‌ها صفر ردیف برمی‌گردانند (DI‑06، DI‑07، DI‑12).
   - ابطال بلافاصله اثر می‌کند، چون هر پرس‌وجو دوباره جدول‌ها را می‌خواند. TTL توکن روی آن اثری ندارد.
   - `revoke_user` دائمی است و قابلیت‌ها و دستگاه‌های کاربر را هم باطل می‌کند.
3. **نوشتن هویت فقط با توابع `SECURITY DEFINER`.** کلاینت روی جدول‌های هویت هیچ INSERT، UPDATE یا DELETE ندارد. توابع زیر فقط برای **مدیر فعال همان مدرسه** کار می‌کنند. کاربرِ مدرسهٔ دیگر برای این توابع «وجود ندارد» (DI‑10).
   - `create_user`
   - `set_user_disabled`
   - `revoke_user`
   - `enroll_device`
   - `grant_capability`
   - `revoke_capability`
4. **`revoke_device`** برای مدیر مدرسه، یا برای کاربری که صاحب دستگاه است.
5. **`bootstrap_school`** اولین مدیر و دستگاه مدرسه را می‌سازد. این تابع فقط برای ابزار تأمین مالک است و به کلاینت داده نشده است (DI‑02، DI‑10).
6. **مسیر نوشتن داده.** INSERT و UPDATE روی `record` فقط درون قابلیت `write` انجام می‌شوند. این موارد رد می‌شوند (DI‑11):
   - جابه‌جایی ردیف به بیرون از اسکوپ
   - نوشتن در مدرسهٔ دیگر
   - DELETE
7. **سخت‌گیری توابع.** همهٔ ۱۶ تابع `search_path = pg_catalog, pg_temp` دارند و هیچ‌کدام برای PUBLIC قابل اجرا نیست. `record` با FORCE RLS است.

## نتیجهٔ آزمون [S]

| شناسه | موضوع | نتیجه |
|---|---|---|
| DI‑01 | مهاجرت با ابزار ردیف ۸۶ | lint تمیز است. یک‌بار اعمال می‌شود و اجرای دوباره کاری نمی‌کند. |
| DI‑02 | کاتالوگ | ۵ جدول RLS دارند. ۱۴ تابع SECURITY DEFINER هستند. توابع داخلی و `bootstrap_school` برای کلاینت قابل اجرا نیستند. هیچ شیء وابسته به ارائه‌دهنده نیست. |
| DI‑03 تا DI‑05 | دامنهٔ مثبت | مدیر A شش ردیف و مدیر B سه ردیف می‌بیند. معلم «حضور، کلاس ۱» دو ردیف و ولی «دانش‌آموز ۱۰» دو ردیف می‌بیند. |
| DI‑06 | کاربر disabled یا revoked | ۰ ردیف در `record`، `app_user`، `device` و `capability` |
| DI‑07 | دستگاه | دستگاه باطل، بیگانه، ناشناخته، بدون ادعا یا بدشکل ⇒ ۰ ردیف. دستگاه دیگرِ همان کاربر کار می‌کند. |
| DI‑08 | نقش دیگر و جعل ادعا | نگهبان و مشاور بدون قابلیت ⇒ ۰ ردیف. ادعای جعلی مدیر یا مدرسه بی‌اثر است. |
| DI‑09 | مدرسهٔ دیگر | ۰ ردیف داده، کاربر و قابلیت، با وجود شناسه‌های یکسان کلاس و ردیف در دو مدرسه |
| DI‑10 | نوشتن قابلیت | ۱۱ رد. اعطا بلافاصله ۲ ردیف را ۳ ردیف می‌کند و ابطال آن را به ۲ برمی‌گرداند. ردپا را فقط مدیر می‌بیند. |
| DI‑11 | نوشتن داده | نوشتن درون اسکوپ پذیرفته می‌شود. همهٔ موارد بیرون از اسکوپ رد می‌شوند. |
| DI‑12 | بدون توکن | ۰ ردیف در همهٔ جدول‌ها |
| DI‑13 | جهش | ۵ جهش، هر ۵ گرفته شدند (جدول زیر). |
| DI‑14 | rollback | rollback با ابزار ردیف ۸۶ اسکیما را حذف می‌کند. اعمال دوباره تمیز است. |

جهش‌ها در تراکنشی اعمال شدند که rollback شد:

| جهش | تغییر | نتیجه |
|---|---|---|
| M1 | نادیده گرفتن disabled/revoked | نشت ۲ ردیف |
| M2 | حذف شرط مدرسه | نشت ۷ ردیف میان مدرسه‌ها |
| M3 | سیاست `USING (true)` | نشت ۱۰ ردیف |
| M4 | دادن INSERT روی `capability` به کلاینت | کاربر به خودش قابلیت می‌دهد |
| M5 | خطای NULL در `revoke_device` | ولی دستگاه معلم را باطل می‌کند |

### نقصی که آزمون گرفت و رفع شد

در نسخهٔ اول، `revoke_device` شرط `IF NOT FOUND OR NOT (d.user_id = me OR d.tenant_id = mt)` را داشت. برای کاربری که مدیر نیست، `mt` برابر NULL است. پس کل عبارت NULL می‌شود و IF آن را «نادرست» حساب می‌کند. نتیجه این بود که هر کاربری می‌توانست دستگاه هر کسی را باطل کند. DI‑07 این را گرفت. اصلاح با `coalesce(…, false)` انجام شد و جهش M5 جلوی بازگشت آن را می‌گیرد.
