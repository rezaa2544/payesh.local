## ۱. راه‌اندازی مستأجر جدید (provision)

```
۱. ثبت مدرسه (نام، پایه‌ها، رشته‌ها، مدیر، تلفن)      ← پنل پلتفرم / self‑serve طبق O‑14
۲. تولید tenant_id (uuid v4، غیرقابل حدس)
۳. تولید کلید مستأجر  DEK_tenant  (۲۵۶ بیت)   → vault، هرگز خروجی API نیست
۴. ساخت پیشوند ذخیره‌سازی  t/<tenant_id>/
   • files/  backups/db/  backups/files/  exports/
۵. صدور پلن و اشتراک (۰۱‑ب) — وضعیت `active` یا `trialing`
۶. ساخت اسکیمای منطقی/ردیف‌های پایه (users: مدیر، settings، پایه‌ها)
۷. ساخت کلید محلی دستگاه‌ها هنگام اولین ورود (۰۳)
۸. ثبت audit: «مستأجر ساخته شد» با tenant_id + actor
۹. اجرای آزمون دود: ورود مدیر، نوشتن ۱ ردیف، خواندن دلتا، شکست RLS مصنوعی
```

قواعد:
- **هیچ مرحله‌ای قابل پرش نیست**؛ شکست در ۹ ⇒ فرآیند rollback و مستأجر `failed_provision`.
- نام پیشوند ذخیره‌سازی **latina کوچک/رقم** و > ۳ نویسه (قید Arvan) — با `t/` و شناسهٔ تصادفی.
- شناسه‌های انسانی (نام مدرسه) هرگز در مسیر ذخیره‌سازی نمی‌آیند.

## ۲. کلید مستأجر (درِ تفکیک رمزنگاری)

| اصل | جزئیات |
|---|---|
| یک DEK به‌ازای هر مستأجر | چرخش سالانه یا در رخداد |
| بسته‌بندی با KEK پلتفرم | KEK در keystore/HSM؛ DEK خروجی نمی‌شود |
| استفاده | رمزنگاری B1/B2 و فیلدهای حساس؛ نه کل پایگاه (RLS جداکنندهٔ منطقی است) |
| مسیر خروج | `export` رمزگشایی‌شده تنها با `owner` + reason (D‑07 بند C) |
| انحلال مستأجر | نابودی DEK ⇒ بکاپ‌ها بی‌مصرف (W2 سراسری) |

> کلید در **کلاینت** فقط برای کش محلی است؛ کلید ابری هرگز به کلاینت نمی‌رسد (پایان F‑04).

## ۳. مهاجرت مدرسهٔ موجود به چندمستأجری

### ۳.۱ مراحل (بی‌قطع‌شدن سرویس)
1. **پیش‌بررسی:** پشتیبان کامل + SHA + شمارش ردیف‌ها و هش هر مجموعه.
2. **افزودن ستون** `tenant_id` با مقدار `T0` (مدرسهٔ اول) — بدون قید.
3. **کپی سایه:** نوشتن مضاعف (dual‑write) با `tenant_id`؛ خواندن از مسیر قدیم.
4. **آزمون تطبیق:** شمارش و هش ردیف‌ها بین مسیر قدیم و جدید برابر.
5. **RLS روشن** در محیط قرنطینه + آزمون دو‑مستأجری (نشت صفر).
6. **کلید مستأجر** ساخت و بکاپ‌ها بازرمزنگاری.
7. **سوئیچ خواندن** به مسیر جدید؛ نوشتن از مسیر واحد (۱۲ §۴).
8. **حذف مسیر قدیم** بعد از ۷ روز پایداری.
9. **گزارش مهاجرت** با SHA پیش/پس و اعداد تطبیق.

### ۳.۲ قواعد قطعی
- هر مرحله rollback دارد؛ در هیچ مرحله‌ای داده حذف نمی‌شود.
- «کپی سایه» فقط خواندن را تضمین می‌کند؛ **تغییرِ رفتار** در گام ۷ است.
- اگر تطبیق ۴ عدد برابر نداد ⇒ توقف و گزارش (نه ادامه با فرض).
- مهاجرت **کد محصول** است؛ پیش از Gate فاز ۳ اجرا نمی‌شود — این سند طرح است.

## ۴. تفکیک فایلها و بکاپ‌ها

| مورد | مسیر | کلید |
|---|---|---|
| فایل آموزشی | `t/<tenant>/files/<sha256>` | DEK_tenant |
| بکاپ پایگاه | `t/<tenant>/backups/db/YYYY-MM-DD.dump.enc` | DEK_tenant |
| بکاپ فایل | `t/<tenant>/backups/files/…` | DEK_tenant |
| خروجی مهاجرت | `t/<tenant>/exports/<ts>.tar.enc` | DEK_tenant |
| متادیتا | پایگاه پلتفرم | — |

- نام فایل با هش محتوا ⇒ deduplication درون مستأجر، بدون افشای عرضی.
- فهرست‌کردن پیشوند یک مستأجر با نشست مستأجر دیگر ⇒ `403` در لایهٔ داده.
