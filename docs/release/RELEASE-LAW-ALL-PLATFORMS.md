## چک‌لیست اجباری پس از هر تغییر (به همین ترتیب)

1. [ ] تغییر در `main` است (merge کامل، بدون conflict).
2. [ ] اگر تغییر کاربرمی‌بیند: افزایش نسخه + `build:release` روی main انجام شده است.
3. [ ] CI روی **main** (نه فقط PR) سبز است: `native-client` ✅، `win32-edition` ✅، `build-and-release` ✅.
4. [ ] هر چهار انتشار وابسته موفق‌اند: `school-native-publish` ✅، `owner-native-publish` ✅، `win32-publish` ✅، `web-app-publish` ✅.
       (انتشارها فقط پس از موفقیت `native-client`/`win32-edition` روی main اجرا می‌شوند؛
        اجرای cancel/skipped یعنی **انتشار انجام نشده** و باید دوباره trigger/پیگیری شود.)
5. [ ] مانیفست‌های زنده خوانده شده‌اند و `commit` آن‌ها **برابر HEAD فعلی main** و `build` آن‌ها از قبلی بزرگ‌تر است.
6. [ ] برای تغییر قابلیت‌محور: داخل حداقل یک بستهٔ ویندوز و یک بستهٔ اندروید، ردّ قابلیت (رشته/کلید یکتا) با grep پیدا شده است.
7. [ ] فقط بعد از ۱ تا ۶: گزارش «انجام شد» به مالک + به‌روزرسانی Notion.

## Fail-Closed

- اگر هر مرحله قرمز، cancel یا skipped بود → کار **تمام نیست**؛ گزارش صادقانهٔ «منتشر نشده» بده و پیگیری کن، نه «انجام شد».
- سبز بودن تست‌ها یا merge شدن PR به‌تنهایی **هرگز** معادل «رسیدن به دست کاربر» نیست.
- این چک‌لیست برای تغییر بعدی خودِ این قانون هم لازم‌الاجراست.
