# سند ۲ — پیشنهاد معماری «پایش-لوکال»

> هدف: همان قابلیت‌های پایش، برای **یک مدرسه**، بدون هزینهٔ سرور/هاست، با یک سیستم داخل مدرسه و گوشی‌های دبیران/دانش‌آموزان/اولیا.

---

## ۱. شش اصلی که همهٔ تصمیم‌ها را قفل می‌کند

1. **کلاینت را نگه می‌داریم، سرور را سبک می‌نویسیم.** رابط ۳۴ هزار خطی و مدل دادهٔ ۸۷ کالکشنی، سرمایهٔ پروژه است؛ زیرساخت ۵۱ هزار خطی ملی، بدهی است.
2. **سرور مدرسه، منبع حقیقت است.** هر دستگاه (گوشی دبیر، تبلت، سیستم دفتر) یک **کش آفلاین** دارد؛ اختلاف فقط از راه همان قرارداد sync حل می‌شود.
3. **هیچ سرویس بیرونی، شرط کار کردن نیست.** بدون اینترنت، بدون پیامک، بدون ابر — مدرسه باید صبح شنبه با برق و Wi-Fi کار کند.
4. **یک مدرسه، یک دیتابیس، یک فایل.** SQLite؛ بکاپ = کپی یک فایل.
5. **ورود باید بدون پیامک ممکن باشد.** پیامک در ایران هزینه دارد و در مدرسه عملاً یعنی «کد را از دفتر بگیر».
6. **اولیا باید بتوانند از خانه ببینند** — اما این یک قابلیت *افزودنی* است، نه پیش‌شرط؛ اگر بودجه/اینترنت نبود، سیستم بدون آن هم کامل است.

## ۲. سه گزینهٔ ممکن (و چرا یکی را انتخاب می‌کنیم)

| # | گزینه | چه چیزی می‌دهد | مشکل |
|---|---|---|---|
| **A** | **سرور کوچک در مدرسه (LAN) + کلاینت آفلاین** | کاملاً مستقل، صفر هزینهٔ ماهانه، سرعت بالا، داده در مدرسه | اولیا از خانه دسترسی ندارند (مگر با تونل)؛ وابسته به یک سیستم |
| B | تک‌فایل روی هر گوشی، بدون سرور (فقط localStorage + همگام‌سازی مستقیم دستگاه‌ها) | ساده‌ترین از نظر زیرساخت | **بدون منبع حقیقت مشترک**؛ حضور و غیاب و نمرهٔ چند دبیر قابل تجمیع نیست؛ اولیا هیچ راهی ندارند؛ تعارض‌ها حل‌نشدنی |
| C | بک‌اند ابری رایگان (Cloudflare/Supabase/Oracle Free) | دسترسی از همه‌جا | وابسته به اینترنت مدرسه، محدودیت/فیلترینگ، حساب کارت‌بانکی، حاکمیت داده، و «رایگان» همیشه رایگان نمی‌ماند |

**انتخاب: A به‌عنوان هسته، با در B (آفلاین) و C (فقط به‌عنوان بکاپ و درگاه اولیا) به‌صورت افزودنی.**

```

                        │                                   │
                   [Cloudflare Tunnel]              [Cloud storage]
                        │  (فقط برای اولیا/دبیر بیرون)      │ (بکاپ رمزنگاری‌شده شبانه)
                        ▼                                   ▲
┌───────────────────── سیستم مدرسه (مینی‌پی‌سی) ─────────────┴─────────┐
│  payesh-local  (Node 22 + SQLite)  :8080                              │
│   ├─ سرو index.html (PWA) + API                                       │
│   ├─ احراز هویت دستگاه (Pairing + PIN) + نقش/اسکوپ                    │
│   ├─ sync (push/pull) + حل تعارض + audit                              │
│   ├─ فایل‌ها (تکلیف/رسید/عکس) روی دیسک                                │
│   └─ بکاپ‌گیر: هر ساعت محلی، هر شب رمزنگاری‌شده به ابر                 │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  Wi-Fi مدرسه (بدون اینترنت هم کار می‌کند)
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
  گوشی دبیران (APK/PWA)   تبلت کیوسک کلاس       گوشی اولیا (PWA)
  حضور، نمره، تکلیف       اسکن QR حضور         نمره، غیبت، اطلاعیه
```

## ۳. سخت‌افزار: چقدر و چه چیزی؟

### ۳.۱ ظرفیت واقعی موردنیاز

| مدرسه | دانش‌آموز | دبیر | اوج هم‌زمانی | سخت‌افزار کافی |
|---|---|---|---|---|
| کوچک | ۳۰۰ | ۲۵ | ~۱۵ گوشی | مینی‌پی‌سی ۴ هسته/۸GB (یا همان PC دفتر) |
| متوسط | ۶۰۰ | ۵۰ | ~۳۵ گوشی | مینی‌پی‌سی N100 / ۱۶GB / SSD |
| بزرگ | ۱۲۰۰ | ۹۰ | ~۶۰ گوشی | N100 یا i3 / ۱۶GB / SSD + ۲–۳ اکسس‌پوینت |

- حجم داده: متن (حضور/نمره/پیام) در سال ≈ **۵۰ تا ۱۵۰ مگابایت**؛ عکس تکالیف اگر استفاده شود، جداگانه ۱–۱۰ گیگابایت.
- بار نوشتن: کل مدرسه در بازهٔ ۵ دقیقهٔ اول هر زنگ، حدود ۴۰ دبیر × ۳۰ دانش‌آموز = ۱۲۰۰ رکورد؛ SQLite این را در چند ثانیه می‌نویسد. **گلوگاه سخت‌افزار نیست، Wi-Fi است.**
- مصرف برق مینی‌پی‌سی: ۶ تا ۱۵ وات ⇒ سالانه حدود ۵۰–۱۳۰ کیلووات‌ساعت (ناچیز).

### ۳.۲ خرید پیشنهادی (یک‌بار)

| قلم | توضیح | برآورد |
|---|---|---|
| مینی‌پی‌سی N100، ۱۶GB RAM، SSD 512GB | Ubuntu Server (بدون مانیتور، headless) | ۱۵–۲۵ م.ت |
| UPS ۶۵۰–۱۰۰۰VA | قطع برق = بزرگ‌ترین ریسک دادهٔ مدرسه | ۳–۶ م.ت |
| ۲ اکسس‌پوینت Wi-Fi ۵GHz (اگر پوشش نیست) | همان SSID، **AP Isolation خاموش** | ۴–۱۰ م.ت |
| دامنهٔ ارزان (اختیاری، برای اولیا/HTTPS) | `.xyz`/`.online` | ~۰٫۵–۱ م.ت در سال |
| کابل/سوییچ/برق‌گیر | — | ۱–۲ م.ت |

> اگر PC دفتر مدرسه قابل استفاده باشد، هزینهٔ سخت‌افزار تقریباً صفر می‌شود (فقط UPS + بکاپ).
> قیمت‌ها تقریبی و وابسته به بازار است؛ معیار تصمیم «کلاس سخت‌افزار» است نه عدد.

## ۴. شبکه و Wi-Fi — جایی که پروژه‌های مدرسه‌ای معمولاً شکست می‌خورند

1. **IP ثابت** برای سیستم سرور (رزرو DHCP در روتر، مثلاً `192.168.10.10`).
2. **نام محلی ساده**: `payesh.school.lan` (رکورد DNS در روتر) یا حتی فقط IP. QR نصب روی در کلاس‌ها = `http://192.168.10.10:8080`.
3. **AP Isolation باید خاموش باشد**؛ در بسیاری از روترها «Guest Network» گوشی‌ها را از سرور جدا می‌کند و همه‌چیز خراب می‌شود.
4. **پوشش**: هر اکسس‌پوینت برای ۳۰–۴۰ دستگاه فعال کافی است؛ برای ۵۰۰ گوشی، ۳ نقطه در نقاط پرتراکم (راهرو/دفتر/سالن).
5. **پهنای باند**: بار اول هر گوشی ۱٫۷ مگابایت برنامه را می‌گیرد (۲۰ گوشی = ۳۴MB، یک‌بار)؛ بعد از آن فقط JSON کوچک.
6. **بدون اینترنت هم کار می‌کند** — اما بهتر است اینترنت برای بکاپ ابری و دسترسی اولیا موجود باشد.
7. **ساعت درست**: انتخاب خودکار کلاس بر اساس ساعت گوشی است؛ اگر گوشی ساعت اشتباه داشته باشد، کلاس غلط انتخاب می‌شود. راه‌حل: در حالت سروری، کلاینت اختلاف ساعت را از `server_time` بگیرد و روی همهٔ محاسبات زنگ اعمال کند (یک تغییر کوچک، اثر بزرگ).
8. **صفحهٔ راهنما/QR**: یک صفحهٔ ساده `http://…/install` که QR نصب برنامه برای اندروید و iOS را نشان دهد.

## ۵. نصب روی گوشی: APK یا PWA؟ (تصمیم فنی مهم)

| گزینه | مزیت | مشکل |
|---|---|---|
| **PWA** (باز کردن آدرس در کروم و «افزودن به صفحهٔ اصلی») | بدون ساخت و انتشار، به‌روزرسانی خودکار | **Service Worker و نصب PWA فقط در HTTPS**؛ روی `http://192.168…` نصب کامل نمی‌شود؛ iOS سخت‌گیرتر |
| **APK (Capacitor) با فایل‌های برنامه داخل بسته** | نیازی به HTTPS ندارد؛ بارگذاری فوری؛ آیکون واقعی؛ آفلاین از روز اول؛ می‌توان CA داخلی را در آن pin کرد | باید APK بسازیم و توزیع کنیم (بدون Play Store هم ممکن است) |
| TWA (روش مخزن اصلی) | استاندارد گوگل | نیازمند HTTPS + assetlinks + انتشار در Play؛ برای مدرسه توجیه ندارد |

**پیشنهاد:**
- **دبیران/کادر: APK اندروید** (Capacitor، بستهٔ ~۳ مگابایت، برنامه داخلش، API روی LAN). توزیع با QR از سرور خود مدرسه (`/app/payesh.apk`) — بدون Play Store.
- **اولیا/دانش‌آموزان: PWA** روی یک دامنهٔ HTTPS (پایین، بخش ۱۱) یا همان APK اگر خواستند.
- **سیستم دفتر/مدیر: همان PWA در مرورگر دسکتاپ** (بدون نصب).

اگر HTTPS را انتخاب کردید (برای PWA): یک دامنهٔ ارزان بگیرید، گواهی Let's Encrypt با چالش **DNS-01** صادر کنید (به IP خصوصی کاری ندارد)، و در DNS محلی همان نام را به `192.168.10.10` بدهید. این کار «HTTPS معتبر + کارکرد کامل آفلاین» را هم‌زمان می‌دهد.

## ۶. هویت و ورود — بدون هزینهٔ پیامک

مدل فعلی پایش «شماره + کد پیامکی + کد ملی» است و صریحاً **رمز ندارد**. برای مدرسه، کد پیامکی یعنی هزینه و وابستگی. طرح پیشنهادی، همان امنیت را با ابزار محلی می‌دهد:

### ۶.۱ سه لایه

```
[۱] پیوند دستگاه (یک‌بار در سال)
    مدیر از پنل، «کارت پیوند» چاپ می‌کند: QR + کد ۸ رقمی یک‌بارمصرف
    دبیر/دانش‌آموز/ولی اسکن می‌کند ⇒ دستگاهش به حسابش گره می‌خورد
    ↓ (توکن ۹۰ روزه در Keystore/Cookie امن)
[۲] قفل روزانه: PIN چهار تا شش رقمی
    ↓
[۳] نشست کوتاه‌عمر (HttpOnly cookie) + نقش/اسکوپ سمت سرور
```

- **کارت پیوند** جای پیامک را می‌گیرد و کد ملی همچنان شناسهٔ یکتاست.
- برای دبیران: کارت در جلسهٔ اول سال تحویل داده می‌شود؛ برای اولیا: همراه نامهٔ آغاز سال یا در جلسهٔ اولیا و مربیان.
- **گم شدن گوشی**: مدیر از پنل «دستگاه‌ها» توکن را باطل می‌کند (یک کلیک).
- **کد پیامکی همچنان به‌عنوان مسیر پشتیبان** می‌ماند: اگر مدرسه بعداً درگاه پیامک گرفت، همان جریان قبلی وصل می‌شود. تا آن روز، «پنل پیامکی دفتر» می‌تواند کد را به متقاضی تلفنی/حضوری بگوید (همان چیزی که در دمو شبیه‌سازی شده).
- **دانش‌آموز بدون گوشی**: مشکلی نیست. حضور و غیاب کار دبیر است. پنل دانش‌آموز اختیاری است.
- **ترجیح فنی**: نشست با توکن مات و جدول سرور (نه JWT) تا ابطال فوری ممکن باشد؛ PIN با `scrypt` (درون Node، بدون وابستگی بومی).

### ۶.۲ ضدسوءاستفاده
- تلاش ناموفق PIN: تأخیر تدریجی + قفل ۱۵ دقیقه‌ای + ثبت در audit.
- نشست‌ها به دستگاه گره می‌خورند؛ کوکی روی IP/UA غیرمنتظره باطل می‌شود.
- هر دستگاه فقط یک نقش فعال در هر لحظه (سوییچ نقشِ چندنقشی مجاز است).
- عملیات حساس (تغییر نمرهٔ تأییدشده، حذف، بستن سال) نیازمند PIN مجدد + ثبت در audit.

## ۷. حضور و غیاب روی گوشی دبیر — جریان اصلی

سه مسیر، هر سه با هم:

| مسیر | چطور | برای چه کسی |
|---|---|---|
| **۱. زنگ‌محور (پیش‌فرض)** | دبیر وارد می‌شود ⇒ برنامه از روی ساعت و روز، کلاس و درس جاری را خودکار انتخاب می‌کند ⇒ فهرست با «همه حاضر» ⇒ تنها غایب‌ها را بزند | اکثر کلاس‌ها، کمترین کلیک |
| **۲. کیوسک QR** | یک تبلت/گوشی قدیمی کنار در کلاس؛ دانش‌آموز کارت QR خود را نشان می‌دهد ⇒ «حاضر» ثبت می‌شود | مدارس ابتدایی/دبیرستان با جمعیت بالا |
| **۳. دستی** | انتخاب کلاس از فهرست من | زنگ فوق‌برنامه، کلاس جبرانی، چندپایه |

**قواعدی که باید در سرور لوکال اعمال شود (نسخهٔ ملی این‌ها را ندارد یا کامل ندارد):**
- هر رکورد حضور، `source` دارد: `teacher` / `qr` / `import` / `manager`.
- ثبت دبیر فقط برای **کلاسی که در آن زنگ به او تخصیص یافته** مجاز است (نه هر کلاسی).
- پنجرهٔ زمانی: ثبت بیش از ۳۰ دقیقه پس از شروع زنگ، برچسب «ثبت دیرهنگام» می‌خورد؛ اصلاح بعدی فقط مدیر با دلیل.
- تأخیر و خروج، **ساعت و دقیقه** دارند و موجه‌سازی جدا (همین حالا در `12-attendance.js` و `PLAN_ATTENDANCE_STATES.md` پیاده شده).
- آفلاین: دبیر در راهروی بی‌پوشش ثبت می‌کند؛ در صف می‌ماند؛ با برگشت Wi-Fi خودکار sync می‌شود (این بخش در کلاینت کامل است).

## ۸. همگام‌سازی و تعارض

- **قرارداد موجود را نگه می‌داریم** (چون آزموده و دقیق است): صف عملیات با `uid` یکتا (idempotency)، `base_version` (OCC)، tombstone برای حذف، و جدول تعارض با UI حل.
- سرور لوکال، `user_id` و `school_id` را **از نشست** تعیین می‌کند و ادعای کلاینت را رد می‌کند (همان ایدهٔ `forged_by`/`user_mismatch` در `server/sync.js`).
- تعارض در عمل نادر است (یک دبیر، یک کلاس، یک زنگ)؛ ولی در دو حالت واقعاً رخ می‌دهد:
  1. دو دبیر هم‌زمان یک رکورد را ویرایش کنند (مثلاً مدیر و دبیر) ⇒ قاعده: **آخرین ویرایش با نسخهٔ صحیح برنده، ولی هر دو نسخه در audit می‌ماند**.
  2. دبیر آفلاین نمرهٔ قدیمی را تغییر دهد و مدیر هم همان را ⇒ نگه‌داشتن هر دو + نمایش «نیازمند تصمیم» به مدیر.
- **Pull دلتا** با `since` + cursor؛ در لوکال هر دستگاه فقط کالکشن‌های مربوط به نقش خودش را می‌گیرد (مثلاً دبیر فقط کلاس‌هایش).

## ۹. پشتیبان‌گیری و تاب‌آوری (مهم‌ترین بخش عملیات)

مدرسه یک سیستم دارد؛ اگر آن از دست برود، سال تحصیلی از دست می‌رود. طرح سه‌لایه:

| لایه | چه چیزی | کجا | تکرار |
|---|---|---|---|
| ۱ | `VACUUM INTO` از SQLite (فایل سازگار و سالم) | همان دیسک، پوشهٔ `backups/` | هر ۶۰ دقیقه، نگهداری ۴۸ نسخه |
| ۲ | کپی کامل (DB + فایل‌ها) روی **فلش/دیسک USB** | USB همیشه وصل | روزانه، ۳۰ نسخه |
| ۳ | آرشیو **رمزنگاری‌شده** (age/rclone crypt) | فضای ابری رایگان | شبانه، ۳۰ روز + ۱۲ ماهانه |

قواعد:
- **بازگردانی را تمرین کنید** (ماه اول هر فصل): از نسخهٔ ابری روی یک سیستم دیگر restore کنید و یک کارنامه بگیرید. بکاپی که تست نشده، بکاپ نیست.
- SQLite با `journal_mode=WAL` و `synchronous=FULL` نوشته می‌شود؛ قطع برق باعث خرابی نمی‌شود، ولی **UPS** باز هم لازم است.
- سیستم باید **سرویس خودکار** باشد (`systemd` در لینوکس / NSSM در ویندوز) که بعد از قطع برق خودش بالا بیاید و مرورگر دفتر را باز کند.
- نگهداری سالانه: در پایان سال، یک «آرشیو سال» (PDF/Excel نمرات و حضور + فایل DB) بسازید و روی دیسک جدا بگذارید (لازمهٔ سیدا/بازرسی).
- رمز بکاپ را **روی کاغذ در گاوصندوق مدرسه** نگه دارید؛ رمز گم‌شده = بکاپ بی‌فایده.

|---|---|---|---|
| **۱. فقط داخل مدرسه** | ولی با Wi-Fi مدرسه یا گوشی فرزند وارد می‌شود | صفر | عملاً «پروندهٔ کاغذی دیجیتال» است |
| **۲. تونل ابری رایگان** (Cloudflare Tunnel + دامنه) | ولی از خانه، **وقتی سیستم مدرسه روشن است** وارد می‌شود | دامنه ~$۵–۱۰/سال؛ تونل رایگان (بدون سقف پهنای باند) | خارج از ساعت مدرسه، سایت بسته است |
| **۳. سیستم همیشه‌روشن** (همان تونل + مینی‌پی‌سی ۸ وات) | ۲۴/۷ در دسترس | ~۱۰۰ کیلووات‌ساعت در سال | باید سیستم و UPS برای ۲۴/۷ باشد |

**توصیه:** سناریو ۳. یک مینی‌پی‌سی N100 در حالت بی‌کار ۶–۱۰ وات مصرف می‌کند؛ هزینهٔ سالانهٔ برق آن از یک لامپ کم‌تر است. با این کار «مدرسه فقط صبح‌ها باز است» به مانع تبدیل نمی‌شود و اولیا شب هم کارنامه را می‌بینند. تونل ابری، ورودی را می‌بندد و لازم نیست در مودم پورت باز کنید.

> جایگزین بدون دامنه: `ngrok` رایگان یک دامنهٔ ثابت می‌دهد ولی سقف پهنای باند ماهانه دارد (برای ۵۰۰ ولی کافی نیست). گزینهٔ بعدی: پورت‌فوروارد + DDNS، که به IP معتبر و CGNAT نبودن نیاز دارد و امنیتش پایین‌تر است.

## ۱۱. دربارهٔ «Terra» (فضای ابری) — صریح

اگر منظور **Terabox** است: ۱ ترابایت رایگان دارد، ولی:
- API عمومی/S3 ندارد؛ یکپارچه‌سازی فقط با ابزارهای غیررسمی/WebDAV و کوکی‌های شکننده انجام می‌شود.
- محدودیت سرعت، قطعی/فیلتر شدن و تغییر سیاست‌ها محتمل است.
- **برای دیتابیس زنده، احراز هویت یا دسترسی اولیا مناسب نیست.**

پس نقش درستش: **مقصد بکاپ رمزنگاری‌شده** — و حتی برای همین هم گزینه‌های مطمئن‌تر رایگان وجود دارد:

| مقصد | حجم رایگان | مزیت | مناسب برای |
|---|---|---|---|
| **Telegram** (rclone backend رسمی) | عملاً زیاد (۲GB هر فایل) | در ایران پایدارتر، بدون کارت بانکی، رسمی | ⭐ پیشنهاد اول برای بکاپ شبانه |
| Cloudflare R2 | ۱۰GB | S3 معتبر، بدون هزینهٔ خروج | ⭐ اگر حساب Cloudflare دارید |
| Backblaze B2 | ۱۰GB | S3 معتبر | جایگزین |
| Google Drive | ۱۵GB | rclone رسمی | آشنا ولی محدودیت API |
| OneDrive | ۵GB | — | کوچک |
| Terabox | ۱TB | حجم زیاد | فقط با رمزنگاری و پذیرش ریسک |

**همیشه رمزنگاری‌شده** (`age` یا `rclone crypt`) — چون دادهٔ دانش‌آموز روی فضای شخصی می‌رود و نباید خوانا باشد.

## ۱۲. استک فنی پیشنهادی

| لایه | انتخاب | چرا |
|---|---|---|
| Runtime | Node.js 22 LTS | همان چیزی که کلاینت/سرور فعلی با آن تست شده |
| HTTP | `node:http` + روتر کوچک، یا Fastify | وابستگی کم، نصب ساده |
| DB | **SQLite** (`better-sqlite3` یا `node:sqlite`) | یک فایل، تراکنش ACID، بکاپ فوری، بدون نصب سرور دیتابیس |
| مدل داده | **جدول عمومی رکورد** + JSON + چند ایندکس، به‌علاوه view های گزارشی | نیازی به ۸۷ جدول نیست؛ با کلاینت یکی‌به‌یکی منطبق می‌شود |
| احراز هویت | توکن مات + کوکی HttpOnly + `scrypt` | ابطال فوری، بدون کتابخانهٔ بومی |
| فایل‌ها | دیسک + مسیر تصادفی + کنترل دسترسی | تکلیف/رسید/عکس؛ بکاپ همراه DB |
| مجوز | همان `authz/write-perms.json` (تولیدشده) | منبع واحد، fail-closed |
| پکیج موبایل | Capacitor (APK) | بدون HTTPS، بستهٔ کوچک، آفلاین واقعی |
| سرویس | systemd (Ubuntu) / NSSM (Windows) | بالا آمدن خودکار پس از قطع برق |

### ۱۲.۱ مدل دادهٔ پیشنهادی (کلید سادگی)

```sql
CREATE TABLE records (
  collection TEXT NOT NULL,
  id         INTEGER NOT NULL,
  school_id  INTEGER NOT NULL DEFAULT 1,
  data       TEXT NOT NULL,          -- JSON کامل رکورد، همان شکل کلاینت
  version    INTEGER NOT NULL DEFAULT 1,
  updated_at TEXT NOT NULL,
  deleted_at TEXT,
  PRIMARY KEY (collection, id)
);
CREATE INDEX ix_records_sync ON records(collection, updated_at);
CREATE INDEX ix_records_school ON records(collection, school_id);
```

- همان ۸۷ کالکشن، بدون ۸۷ جدول؛ کلاینت بدون تغییر با آن حرف می‌زند.
- گزارش‌ها با `json_extract` و چند view.
- بکاپ = یک فایل؛ انتقال سال = یک کوئری.
- اگر روزی بزرگ شد (خیلی بعید برای یک مدرسه)، مهاجرت به Postgres آسان است.

### ۱۲.۲ API هایی که باید پیاده شوند (کل سطح تماس)

| متد و مسیر | کار |
|---|---|
| `GET /api/health` | تشخیص خودکار حالت سروری توسط کلاینت |
| `POST /api/auth/pair` → `POST /api/auth/pin` | پیوند دستگاه و ورود |
| `GET /api/auth/me` · `POST /api/auth/logout` | نشست |
| `POST /api/sync` | صف نوشتن (idempotency، OCC، gate نقش/فیلد، audit) |
| `GET /api/v1/pull?since=` | دلتا + tombstones + `server_time` |
| `GET /api/students/:id` | پروندهٔ تک‌دانش‌آموز با اسکوپ |
| `POST /api/attendance/qr` | کیوسک QR |
| `GET /api/admin/backup` · `POST /api/admin/restore` | پشتیبان/بازیابی از UI |
| `GET/DELETE /api/admin/devices` | مدیریت دستگاه‌ها و ابطال |
| `GET /api/install` · `GET /app/payesh.apk` | صفحهٔ نصب و توزیع برنامه |

همین ۱۱ مسیر، کل نسخهٔ لوکال را می‌سازد. (مسیرهای اضافی مثل `bell`, `reports`, `public-report` بعداً و بر اساس نیاز.)

## ۱۳. امنیت و حریم خصوصی

- **TLS**: برای APK با بستهٔ همراه، رمزنگاری لایهٔ انتقال «خوب است» نه «اجباری»؛ پیشنهاد: گواهی خودامضا با CA داخلی و **pinning در APK** تا دادهٔ نمره روی Wi-Fi خوانده نشود. برای مرورگر، دامنه + Let's Encrypt.
- **دسترسی شبکه**: API فقط روی LAN گوش بدهد؛ پورت ۸۰۸۰ از بیرون بسته باشد (به‌جز تونل).
- **رمزنگاری دیسک**: BitLocker/LUKS — اگر سیستم دزدیده شد، دادهٔ دانش‌آموزان خوانا نباشد.
- **حداقل‌سازی داده روی گوشی**: بعد از خروج از حساب، کش پاک شود؛ PIN برای باز کردن برنامه.
- **audit**: هر تغییر نمره/حضور/حذف با کاربر، دستگاه، زمان، مقدار قبلی و جدید.
- **IDOR**: `byId` کلاینت شناسه‌محور است (خود مخزن TODO گذاشته)؛ در لوکال، اسکوپ **سمت سرور** روی هر درخواست اعمال می‌شود و کلاینت هرگز مرجع امنیتی نیست.
- **حریم خصوصی اولیا**: هر ولی فقط فرزندان خودش؛ پیام‌ها و مشاوره جدا؛ ارزشیابی دبیر ناشناس و تجمیعی (که در مخزن پیاده شده).
- **حقوقی**: رضایت ولی برای انتشار داده در پنل، سیاست نگهداری (چند سال)، و حق حذف — اسناد `privacy.html` و `IRAN_COMPLIANCE_PACKAGE.md` مخزن قابل استفاده‌اند.
